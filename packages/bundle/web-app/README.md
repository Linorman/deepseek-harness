# `@clocky/clocky-web-app`

English | [中文](README.zh.md)

The clocky browser-surface bundle. [`cordis.patch.yml`](cordis.patch.yml) rides over [`clocky-base`](../base/README.md): it sets the coding persona, inserts the Web host rows (webserver, API gateway, workspace, projection cache, storage) and the browser plugin roster, the always-on client-plugin reload chain ([`clocky-client-hmr`](../../client/hmr/README.md), idle until a rebuild watcher rewrites client bundles), and mounts this package's `web-runtime` glue plugin (config `{openBrowser, printUrl, surfaceContext, trustedHosts}`). That plugin resolves the built frontend dist through `@clocky/clocky-web-frontend`'s exports, samples bind-dependent LAN trust once, provides it as `webRuntime` to the browser-trust fence and client roster, mounts the [`frontend-static`](../../host/frontend-static/README.md) fallback owner, and registers the harness-source and web-surface prompt sections plus the bash-visible `CLOCKY_WEB_URL` runtime variable when `surfaceContext` is true. After its Loader tree settles, it prints the `clocky web:` URL line when `printUrl` is true and opens the canonical host URL in the default browser when `openBrowser` is true and the inherited `SSH_CONNECTION` and `SSH_TTY` are blank or absent. An SSH launch keeps the URL line but suppresses browser handoff because the SSH client or editor owns the local forwarded address. Immediately before a handoff, the runtime prints `clocky web: opening the default browser; pass --no-open to disable`. A short-lived Node helper runs the maintained platform opener with the canonical scrubbed child environment. On Windows it stays alive until the short-lived PowerShell launcher exits, because `open` reports spawn before that launcher has handed the URL to the shell; elsewhere the helper stops after the opener accepts spawn. A helper failure writes a credential-safe diagnostic to stderr and leaves the owner-only temporary handoff document available until its TTL, so the user can open that document manually; no path waits for the browser to exit. This bundle also owns the app command line: the ordinary `web-startup` provider ([`src/startup.ts`](src/startup.ts)) injects `ctx.cmdlineArgs` ([`clocky-cmdline`](../../boot/cmdline/README.md)), parses `--host`, `--port`, repeatable `--trusted-host`, `--no-open`, and the app's `--help`, then provides `webStartup`; browser opening defaults on for local launches, and `--no-open` turns it off for this invocation. It rejects `--host 0.0.0.0` before publishing that service because the CLI intentionally does not support all-interfaces binding yet. Flag-configured rows inject the service and read it directly from lazy config, so nothing binds a port before argument resolution and `clocky --profile web --help` starts no server. [`clocky-headless`](../headless/README.md) is a sibling surface over the same base and does not mount this bundle.

`productPrincipalProvider` is shared with the Web connection row. For the shipped local provider, browser handoff creates an owner-only temporary HTML document below the Harness home; the platform opener receives only that document's `file:` URL, and the document posts its credential body once to the loopback bootstrap endpoint before redirecting to the app. Printed/manual URLs, browser-launch arguments, diagnostics, and browser persistence carry no credential. The document is removed after the accepted exchange, expiry, or runtime teardown; `browserHandoffDirectory` and `browserHandoffTtlMs` configure its private location and lifetime. An unavailable configured provider suppresses browser handoff.

The same host composition mounts the local Team path: SQLite-routed logs at `$CLOCKY_HOME/team-storage.sqlite`, the durable Hub, direct v3 channel, in-process activation and local Link delivery, scoped Team tools, and `ctx.teamRuns`. Its JSON domain storage remains separate from Team journals. It also mounts the shared-workspace registry, whose `process.cwd()` root is a fallback while the enabled durable `workspacePath` selects the folder chosen for each Team, the task-assignment adapter, and a bounded scheduler. The provider canonicalizes that selected root and refuses a worker Session with another `cwd`; it never rewrites the Session or substitutes another directory. `team-run` starts with one lazy `minimal` worker and lets the coordinator grow the pool to 32 with `team_worker_pool_set`; independent tasks are assigned in parallel and ready tasks beyond current capacity stay queued without stalling the Team. A reviewer is provisioned when needed, while the coordinator retains its request-selected or default preset. Mutating task reports carry provider-owned changed-path/artifact manifests through the explicit report-only publish boundary. The browser roster mounts `ui-team`; client boot begins with a local Team draft, and `team.start` is the user task entry. Objective, budget, and phase stay in the Team detail popover, while `/goal` is the scoped Team command in the coordinator transcript. The base same-Session Goal service, automatic driver, command, model tools, and GoalBar are absent. The default coordinator receives `get_goal`, `update_goal`, `team_final`, `team_worker_pool_set`, `team_task_start`, `team_task_wait`, `team_task_list`, `team_task_watch`, `team_task_cancel`, `team_task_propose_owner`, `team_workflow_start`, and `team_workflow_wait`; direct subagent, legacy workflow-script, and Ralph tools are absent from shipped Web composition. A deployment can mount legacy workflow scripts only in an explicit custom composition.

## Default Simulation

The stable `web-simulation` group owns `web-simulation-service`, `web-simulation-local`, `web-simulation-team`, `web-simulation-product`, `web-simulation-administration` and `web-ui-simulation`. It reuses the existing storage-log, Team, activation, principal, model and Session services. Standard profiles inherit it through this bundle without rewriting their manifest or patches. Native tools register only inside the `simulation-company` and `simulation-world` presets, not ordinary Team/minimal agent catalogs. The `simulation-administration` entry publishes three editable `clocky.world/v1` templates: software studio, research laboratory and reading association. Each starts with an independent director, two organizational actors, a review committee and a vacant contributor position. The original `company-procurement-v1` template remains available separately.

Native worlds use provider `web-local`, SQLite and `clockyHomePath('simulations')`; the directory and command streams are `web-simulation-directory-v1` and `web-simulation-commands-v1`. Installed models bind to the live Agent default. Browsing and boot allocate no run or writer and perform no inference; creation prepares a paused world. The Simulation model pool admits one request with 16 queued; scheduling retains the administration defaults of 50 ms productive batches and 1000 ms retry observations, and directory watches retain 2000 ms polling.

A fresh Web installation boots without a model provider. Open Simulation, choose the installed template and enter a draft. Configure a provider in Models and explicitly save its default provider/model; no catalog row is selected automatically. Returning to creation preserves the draft and reruns the metadata-only check. Explicit Create prepares the paused world; only a separate Start admits inference. Both drivers require provider-default reasoning; clear any explicit reasoning override in Models. For a World, choose New world, select a template, edit it and click Check definition. After configuring a model, return to the retained draft and check again before creating it. World preflight resolves every installed runtime profile to the saved default and includes that concrete route in the reviewed hash. A changed default requires a new preview; accepted commands and cold recovery keep their original model.

The procurement template starts with two actors and permits 16 entities / two residents. Its 16,384-token request reservation and 262,144-token interval budget admit 16 complete reservations per 60 simulated minutes, covering the procurement decision chain with bounded retry headroom. Context is limited to 65,536 bytes, knowledge to 16,384 bytes / 16 records, ingress to 16,384 bytes, a decision window to two decisions / 16 operations, and time to 360 minutes; completion is due at 30. Pending events/interactions/decisions are capped at 64/32/32. Checkpoints admit 32 drain rounds and three attempts. Remaining exact policy bounds live in the production patch. The preset exposes only native Simulation tools.

World starters use the separate `simulation-world` preset and only simulated external interactions. Their catalog bounds each run to 32 entities, three residents, 32 world requests and 360 simulated minutes; the interval token budget is 1,048,576 and the Team lifetime token budget is 2,000,000. Actual Team ceilings may reduce these bounds. [Installed metadata](src/world-catalog.ts) owns the complete limits and [starter definitions](src/world-scenarios.ts) own the editable goals, permissions and advisory institution. The Web package ships these definitions without importing test fixtures or requiring an enabling overlay.

To keep a custom Simulation deployment, explicitly disable the default group before mounting its own services:

```yaml
- id: web-simulation
  disabled: true
```

Keep the custom provider identity, storage root and stream names unchanged. Do not merge roots or reuse the default stream names for unrelated data. Group disable retains all persisted data and leaves Team available. Headless does not include this Web bundle.

New World runs use `bounded-v1`: a 65,536-token request reservation, 4,096-token output cap, 2,048-token margin and 1.5 input estimate factor. The `simulation-world` preset reuses BasicCompaction with a 32,768-token trigger, 8,192-token retained tail and 2,048-token summary cap. A deterministic policy records initial institution notices; ordinary observation returns the current context reference, while `detail: full` repeats its body. Saved legacy runs retain their original protocol and allowances without automatic migration or start.

## Model retry defaults

Web uses the shared bounded normal default of five eligible retries after the initial request. The `test-provider` route and settings-added pi-ai routes use that default when they omit `retryPolicy`; explicit provider policies still win. Web adds no retry-specific composition override, so the same omission behavior applies to non-Web profiles.

## Model Experience

### Harness-source and Web-surface context

#### What the model sees

When `surfaceContext` is true, the `harness:source` section identifies the on-disk Harness implementation without claiming it is the working directory, and the `app:web-surface` global section (order −98) orients the model to the GUI: the canonical local URL, the "this page" referent, the update contract (the reload receiver is always on; no-refresh reloads additionally need the `pnpm run dev:web` watcher), and the instruction not to start replacement servers. `CLOCKY_WEB_URL` additionally appears in the managed bash environment with its description, resolved per invocation from the live server. When it is false, neither section nor the variable is registered.

#### Token effect

One source line and one prompt paragraph per session plus two managed-environment variable lines; constant per process.

#### KV Cache effect

The prompt section sits near the system prompt's head and is stable for the life of the process (the port is a boot fact), so it does not invalidate the cache across turns.

## Known Limitations and Deferred Work

- **The frontend dist must be built** — `require.resolve` of the dist fails loud at activation with a build hint; there is no source-serving fallback.
- **`lanAddresses` is a boot-time snapshot** — interface changes after boot are not re-advertised; the printed LAN URL always matches the configured trust fence.
- **Only handoff startup is observable** — observation ends when the platform opener accepts spawn, except that Windows waits for its short-lived PowerShell launcher to exit; a later browser exit is not reported, and the printed URL remains the manual fallback.
- **SSH forwarding owns the browser URL** — the printed canonical URL names the remote host's loopback endpoint; automatic handoff is suppressed, and the SSH client or editor must expose and open its local forwarded address.
- **Browser command overrides are launch-only** — a discovered `.env` may not set `BROWSER`; only an inherited value may reach an opener path that honors the variable, so a checkout cannot choose an executable for automatic handoff.
