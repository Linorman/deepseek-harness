# @clocky/clocky-team-agent-client

English | [中文](README.zh.md)

`@clocky/clocky-team-agent-client` exports `FixedBindingTeamAgentLinkDelivery`, a Consumer that delivers accepted direct, basic-channel, workflow, and task-assignment channel Envelopes for one exact `{ agent, binding }` pair. It uses Team Link, Agent, Session, and channel protocols; optional local workspace consumption also uses the Team and workspace registries. `TeamAgentClient` is the local wrapper: it resolves a live Agent's Session-header `teamId` and `participantId` against durable activation state, then owns one fixed delivery Consumer for that binding. The package depends on `clocky-team`, `clocky-team-link`, the channel protocols, Agent, Session, and LLM contracts, never on `team-hub`, AgentLoop internals, or an AgentRuntime provider.

Each fixed delivery Consumer receives `onInvitation()` before ordinary delivery. It checks its current Agent/binding, exact manifest fingerprint, role, and supported adapter version, then calls `acknowledgeChannelInvitation()`. Task-assignment invitations also match the frozen activation and Session. Confirmation creates no model input or Envelope receipt. Ordinary delivery still claims the accepted intent and flushes its Session before receipt.

## Local delivery

`TeamAgentClient` subscribes before scanning already-live Agents. It reconciles each Session-header pair against `TeamStateSnapshot.activations` and accepts only an exact `running` or `idle` epoch for that Session. A `starting`, `stopping`, or `offline` epoch receives no channel input. Each accepted binding starts `FixedBindingTeamAgentLinkDelivery`; its caller owns binding discovery, while the fixed Consumer owns Link connection, notification handling, claim, inbox admission, flush, receipt, soft interrupt, reconnect, and close. With `consumeWorkspace` enabled, the fixed Consumer reads durable allocation metadata and observes allocation changes for its exact binding. The configured Link owns pending-page replay and cursor watches. For a `direct` v1/v2/v3 single-recipient or v4 subset/broadcast `message` Envelope notification, the Link's `claim()` is the final awaited admission check with exact Team, participant, activation, Session, channel, and Envelope identities. `undefined` has no local inbox effect. A returned claim must still match the local binding, active direct channel, Envelope, and delivery intent before the client derives a deterministic `team-envelope:<EnvelopeId>` message and records `TeamEnvelopeSource` on it; the source retains the accepted delivery intent so Host queue projections can distinguish pending steering from non-waking Team context. Direct v3/v4 parses its ordered text and image-reference blocks, then places them after the durable sender prefix without changing their order. Direct v2/v3/v4 `final` Envelopes never enter a local Agent inbox or create a local receipt.

For a consult, discussion, workflow, or review notification, the claim must carry the Hub-rendered `team/channel-view`. The client appends that required Session event and queues its stable derived user message behind a pre-step persistence barrier, then flushes before permitting a model step or acknowledging the Envelope; it never re-renders the live channel, adapter, or view policy. A missing or mismatched view rejects. A repeated claim must match the stored field values and ordered content; JSON object-key order does not change the view. A `task-assignment` v1 notification additionally checks its task, assignee, activation, and Session against the local binding, then calls `claimTaskAttemptStart()` through the Link. The Link derives the caller identity and the Hub returns the same running task after a replayed start claim. Only a returned task with the assigned lease, wake channel, and started timestamp enters the target inbox as a deterministic `team-task-assignment:<EnvelopeId>` message with `TeamTaskAssignmentSource`; the task channel always uses `followup`.

The client maps `context` to non-waking `inject`, `turn` to `followup`, and `steer` to `steer`. Direct and task sources install an Envelope-specific `agent/pre-step` barrier until `ctx.sessions.flush()` persists the target Session; a failed flush leaves the receipt pending. Non-direct channel views use the same persistence barrier for their derived inbox message. Replay reuses the stored view and does not enqueue it again after its claimed input reached a durable model step; a fork seed does not count as consumption by the new Agent. A successful delivery calls the Link's `acknowledge()` with the claim's channel cursor. A task-start success followed by Session or receipt failure remains replayable: the durable pending Envelope retries its idempotent start claim before it is admitted or acknowledged. When configured, the client consumes the exact task workspace allocation after the start claim, retains its root in an Agent-keyed live lease, and releases it only after terminal task settlement.

When a task Agent's turn ends with the provider's `max-tokens` reason, the client re-reads the exact running lease and queues a bounded continuation that names the same task and attempt and instructs the Agent to call `team_task_report`. A terminal task or replaced activation clears the continuation budget; repeated truncation stops after `maxTaskOutputContinuations` and settles the still-running attempt as a bounded worker failure instead of creating an unbounded wake loop or waiting for lease expiry.

For an exact binding-targeted soft interrupt, the client calls `Agent.cancel({ kind: 'user' }, { keepInbox: true })`, then calls the Link's `acknowledgeInterrupt()` without waiting for turn completion. The interrupt adds no inbox source or model-visible input; a failed acknowledgement remains pending for Link replay.

When a matching durable binding or Agent becomes live, the client connects before accepting Link notifications. A failed connection or rejected Link `done` reconnects after `reconnectDelayMs` only while the exact binding remains current. Replayed or repeated Link notifications treat an Envelope as admitted only when it reached durable `user/message`, remains in the live inbox, or completed a flush that is awaiting receipt; a claimed message rejected before `user/message` is admitted again on retry. An already-flushed source is flushed and acknowledged without another inbox write. For each exact current binding, the client retains a private activation-proof lease and forwards only the final provider-reported `assistant/message.usage` facts to `ctx.teams.recordUsage()`; the Hub revalidates that binding and derives Team/Participant/Session/timestamp before budget policy or durable accounting. The lease is revoked when its binding is released or the client closes; the Hub replaces a chunk/final duplicate and enforces frozen Team budgets. Closing, Agent disposal, and inbox discard reject any matching pending pre-step barrier. An unbound, stopping, offline, or departed target, broadcast, multi-recipient draft, unsupported channel protocol, and a Link without a local Agent remain outside this local path.

When a remote WebSocket Hub sends a cooperative termination request, the fixed delivery passes its optional `onTerminate` callback; absent a custom callback it cancels the exact Agent with `keepInbox: true` and waits for `whenIdle()`. The connection does not schedule a reconnect after an accepted endpoint termination, while the owning AgentRuntime provider remains responsible for disposing the Agent/process and proving offline termination.

## Configuration

`consumeWorkspace` defaults to `false`; enable it when this local binding must consume durable task allocations. It requires the Team runtime and workspace registry for allocation mutations. `workspaceMutationMaxAttempts` defaults to `3` and accepts a positive safe integer. Each reserve, activation, release-intent, preservation, or release-confirmation mutation retries only `TEAM_CURSOR_CONFLICT`, taking the Team cursor and current allocation revision from one fresh snapshot and issuing a new exact proof. Reservation retains its admitted task revision and attempt. Provider release and reconciliation run outside these retry loops; a successful physical release remains known to the live owner until durable settlement, so a later confirmation retry does not release the root again. A confirmation rejected with a `TeamError` remains pending for an explicit owner retry; it does not trigger provider reconciliation.

`linkProvider` selects the Team Link provider and defaults to `local`. `reconnectDelayMs` defaults to `100` and bounds the delay before a current binding reconnects after a Link failure. `maxTaskOutputContinuations` defaults to `3` and bounds automatic task wakes after a provider output limit. `disposalTimeoutMs` bounds settlement of local deliveries and Link closure accepted before this plugin unloads; it defaults to `5000`. Unload closes new delivery admission first, cancels pending reconnects, stops each Link subscription, rejects pending pre-step barriers, and preserves any inbox message already appended by an accepted delivery. A claim rejected after its Link retires leaves the Envelope pending for replay and does not fail disposal; a current Link still propagates claim errors. A disposal failure or timeout reports incomplete shutdown. While admitted work or mapped allocations remain unsettled, the closed delivery retains its workspace proof source, Agent lease, unavailable marker, and rejecting pre-step listener. The activation-disposal owner can retry through the Core workspace settler; successful release or explicit preservation, after admitted work drains, revokes these resources once. The original close promise retains its failure result. Setup that finishes after closing abandons an unreserved preparation or settles its reserved/materialized allocation without publishing a new Agent root. A restored allocation that fails activation or root publication is released through durable release intent; failed physical cleanup records preservation. See the [recovery and settlement decision](../../../.agents/notes/implemented/bug-fix/2026-09-05-agent-client-recovery-settlement.md).

An allocation may expose `onLoss()` for exact provider observations. The current Agent Client records its world and retained artifacts as `unavailable`, stops only the task's proven turn, and releases a confirmed expired world before attempt settlement. Unconfirmed execution remains stalled; a missing path never becomes a replacement world. [Loss ownership](../../../.agents/notes/implemented/architecture/2026-09-08-e2b-workspace-loss-settlement.md).

## Model Experience

### Direct and task-assignment Envelope delivery

#### What the model sees

The target Agent receives a direct v1/v2 message in the form `Direct message from <ParticipantId>:\n<text>`. A direct v3/v4 message starts with the text block `Direct message from <ParticipantId>:\n`, followed by its exact ordered text and durable image-reference blocks. Non-direct delivery receives the Hub-rendered `team/channel-view` content, including its Team/channel/Envelope provenance and any review fence. A task message has the form `Team task assignment: <subject>\n\n<description>\n\nTask: <TeamTaskId>\nAttempt: <TaskAttemptId>`. The Agent Client flushes each model-visible input before acknowledging its source Envelope, so Session history reconstructs the exact input.

#### Token effect

One direct delivery adds its sender prefix and either text or ordered text/image content to the target Agent's next context, turn, or step. One task assignment adds its subject, description, task id, and attempt id to the target Agent's next turn.

#### KV Cache effect

The message is dynamic input and does not modify the Agent's static prompt prefix.

## Known Limitations and Deferred Work

- This Consumer handles direct v1/v2/v3/v4 messages, Hub-rendered consult/discussion/workflow/review views, and task-assignment v1 delivery to a local Agent; direct finals still require a TeamRun or human delivery Consumer. It does not own Team admission, Link authentication, channel adapters, Agent placement, or pending-page replay.
- A remote Link may notify this Consumer only when its binding has an exact local Agent. Remote endpoints and non-local Agent execution remain separate Consumers.

### Single-task cancellation

Single-task cancellation discards only matching queued assignment input. The client reconstructs task claims from the Session log, waits for the selected turn to end, releases its allocation, and acknowledges through the Link. Proven queued-only input settles independently of other running work. A delayed notification cannot interrupt a later task. [Cancellation ownership](../../../.agents/notes/implemented/architecture/2026-09-06-exact-single-task-cancellation.md).
