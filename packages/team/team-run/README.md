# @clocky/clocky-team-run

English | [中文](README.zh.md)

`@clocky/clocky-team-run` owns the local default Team topology at `ctx.teamRuns`. It creates its root through a one-shot `TeamSystemRootCreationProof` that binds the complete resolved root payload; the Hub records the derived system source as durable `createdBy` provenance. It then creates a durable human participant, an active local coordinator, and the configured initial pool of provisioned inactive workers; opens a direct v3 human/coordinator channel; activates the coordinator through `ctx.teamActivations`; and accepts trusted human text/image content only after that topology commits. It retains a source-scoped ordinary-post proof for each current run, so `postHumanInput()` admits only its exact active human-to-coordinator direct-v3 message and never accepts a caller-selected sender. `TeamSystemTopologyProof` issues one exact bootstrap invite, membership phase, or direct-channel operation before publication; after publication it issues only a declared worker-pool invite, activation, retirement, or reviewer invite/phase operation. Every token is runtime-only, one-shot, and revoked at publication, release, creation failure, or disposal. The same coordinator authority can compile a JSON-serializable `TeamWorkflowPlan` into a durable task DAG and versioned workflow channel; no shipped workflow path executes model-written JavaScript.

After this service itself settles a Team through completion or cancellation, it retains only an in-memory terminal archive owner for that Team. `archiveTerminal()` mints a one-shot `TeamSystemArchiveProof` scoped to the Team and supplied cursor, then delegates the durable marker to the Hub; successful Host retries remain idempotent while this owner remains live. A Team id, terminal snapshot, root provenance, roster, new TeamRun service, or process restart cannot recreate the owner. `close()` and plugin disposal clear both owners and outstanding archive proofs.

The service is not an Agent loop. `@clocky/clocky-team-agent-client` delivers the human Envelope to the coordinator Session, and the coordinator must use `team_final` to append an explicit human-addressed `final` Envelope. `team-run` registers a source-scoped `TeamSystemFinalReceiptProof` resolver and `waitForFinal()` retains one proof for one current local run's Team, human/coordinator pair, and default channel. The Hub accepts that proof only for the exact active two-member direct-v3 channel and a nonempty coordinator `final` addressed solely to that human. `waitForFinal()` records completion intent, persists the exact result through `admitTeamFinalResult()`, and then records its human receipt. A paused or blocked objective, unfinished work, or completion-policy denial prevents result admission. With the closure driver mounted, the run releases its local leases and delegates channel closure and terminal settlement to the driver. Recovery first appends a missing result admission, then uses a fresh cursor to repair its receipt. Without the driver, local channel cleanup uses `TeamSystemFinalizationCleanupProof` after coordinator release. Team completion still requires the resulting durable state to be quiescent. `TeamSystemCancellationCleanupProof` is separate: after durable cancellation and local release, it can affect only the exact pending task or active channel selected from that cancellation. Each completion or cancellation attempt, and a pre-publication creation failure, uses a separate ephemeral `TeamSystemClosureProof`. Each carries only its exact TeamRun scope, is revoked after the Hub call, and becomes durable `{ kind: 'system', name: 'team-run' }` attribution rather than impersonating the human or coordinator. `waitForFinal()` resolves its Team only from this process's current run map: a detached Team id fails closed, and a recovery owner must `resume()` before it can obtain a new current-run proof and wait for or settle the final result. If a coordinator turn reaches the provider output limit, TeamRun queues a bounded continuation on the same Agent Session so pending worker coordination can finish without a manual wake. `maxCoordinatorOutputContinuations` limits that recovery; exhaustion is recorded as the normal `FINAL_ANSWER_MISSING` stall, which leaves the Team observable and stoppable instead of waiting forever.

Creation waits for durable channel admission before returning an active handle or posting initial input. System-owned human participants are confirmed by the actual TeamRun result Consumer. A product-principal owner must supply the runtime-only `admitHumanChannel` capability: Host and SDK Consumers validate the exact supported manifest and issue a complete-payload human proof within their current authenticated call. Returning without a durable acknowledgement fails creation. Callback failure or cancellation uses the existing activation-release and failed-creation cleanup; a failed start releases its retry key, while an accepted same-key request returns its original result. The capability never enters JSON or the start fingerprint. Workflow compilation also waits before binding its channel.


Principal-owned finals require the [durable human inbox](../team-human-client/README.md): the Hub persists exact final content there before recording sink admission and receipt. The default human grant includes `dispatch` for inbox access. System-owned unattended runs retain the separate closed result sink; browser display acknowledgement does not delay Team completion.

`maxChildTeams` optionally freezes a lifetime descendant-count budget into new root Teams. Zero rejects child creation; omission adds no count ceiling. A delegated child under a bounded root must specify `budget.maxChildTeams`, with zero selecting a leaf child.

Task waits, workflow waits, and blocking task watches reject with `TEAM_RUN_REVIEW_FAILED` when the exact local reviewer turn ends without an accepted response. They recheck task revision before reporting the failure and leave review state unchanged; an already durable response remains eligible for scheduler recovery. A stalled Team rejects a still-pending wait with `TEAM_RUN_NOT_QUIESCENT`. Neither error cancels or repeats worker execution.

`maxLiveActivations` freezes the root’s simultaneous startup/epoch capacity; child requests explicitly allocate a subset including their coordinator and idle members. Shipped headless/web roots select `maxChildTeams: 32` and `maxLiveActivations: 128` in Cordis configuration.

## Configuration

`channelPageSize` is a positive safe-integer setting that defaults to `128`; `waitForFinal()` uses it to read the final-output channel WAL through bounded provider pages.

`activationProvider`, participant display names, `workerCount`, `maxWorkerCount`, reviewer name/capability/preset, `templateId`, `templateVersion`, `placementDefaults`, worker capability/task limits, `workerPreset`, prompt orders, `receiptRetryAttempts`, `humanInputRetryAttempts`, and `maxCoordinatorOutputContinuations` are configuration fields. `placementDefaults` is an optional JSON-friendly restriction set (`participantIds`, `roles`, `providers`, `presets`, or `models`) frozen into participant tasks that omit an explicit placement; an explicit task placement wins. `maxCoordinatorOutputContinuations` defaults to `3` and bounds same-session recovery after a provider output limit. `workerCount` is the initial nonnegative safe integer pool size and defaults to one; `maxWorkerCount` is the nonnegative deployment ceiling and defaults to 32. The coordinator can grow or shrink the durable pool with `team_worker_pool_set`; slot zero remains `worker`, later slots use `worker-2`, `worker-3`, and so on, and idle excess slots are retired after task pressure drops. A later scale-up reuses retired role numbers before allocating a new role, so repeated resizing does not consume the participant limit unnecessarily. The shipped Headless and Web profiles start with one worker and allow up to 32. Independent tasks are admitted without waiting for a free slot, and the scheduler assigns them concurrently whenever active workers are available; a saturated or capped pool returns explicit queue status instead of stalling the Team. The initial Team rules retain the configured template id/version as product-topology provenance until the core Team template record lands. `create()` uses its optional `selection` and named `preset` for that coordinator only, otherwise the current `agentDefaultModel` selection and no preset; its optional positive `maxTokens` applies to that coordinator's requests without changing either default. A default-worker task requires a configured `workerPreset`; the selected activation provider resolves that exact preset during lazy worker activation and rejects an unavailable preset without falling back to the coordinator or roster default. When `reviewerPreset` is configured, a task with declared write scopes lazily provisions and activates a reviewer Participant and freezes a participant-review route.

The coordinator delegates independently deliverable and verifiable work when it saves time or context. Small tightly coupled work can use one executor. Each brief names inputs, output, scope, validation, and handoff; concurrent writers use disjoint scopes. The prompt supplies the configured workflow worker capability and requires retained evidence before synthesis, without duplicating tasks still retrying or cancelling.

`start()` combines topology creation with the first trusted human Envelope. A caller supplies one sender-scoped idempotency key; matching retries return the same Team and Envelope while the current local owner remains available, while a different request using that key fails. `postHumanInput()` accepts the same optional key and re-reads a channel cursor up to `humanInputRetryAttempts` after an intervening receipt or reply, so a retry cannot duplicate a durable input.

Default-worker task creation applies `receiptRetryAttempts` separately to worker-pool preparation, each reviewer membership/activation step, and task admission. Concurrent coordinator admissions are serialized only around pool topology and task creation so every independent task contributes to automatic scale-up; worker execution remains parallel. A successful reviewer step resets its cursor-conflict count; completed participant preparation does not consume the task mutation's retries. Every attempt re-reads Team state and issues a fresh proof, and non-cursor failures still propagate.

`resume({ teamId })` re-owns an active or stalled durable default Team after its previous coordinator activation settled offline. For a stalled Team it mints one source-scoped phase proof that can restore only that Team to `active`, then reuses the persisted coordinator Session, model route, preset, and default channel and mints a new activation epoch; a terminal or archived Team is not resumable.

`cancel(teamId)` first sends the Hub's typed cancellation command with an ephemeral TeamRun cancellation proof. Only after that command durably closes admission does it release local leases and use fresh cancellation-cleanup proofs for each exact retryable task or channel cleanup; if an unrelated accepted Team record advances the cursor first, it re-reads and retries the same idempotency key within `receiptRetryAttempts` with a new proof. If the initial command is not accepted, the service retains local ownership so the caller can retry without leaving an ordinary quiescing Team behind.

`requestCoordinatorInterrupt(teamId)` is the narrow product interrupt path used by ACP cancellation. It issues a one-shot source proof that derives only this run's human requester and default coordinator target; non-active or detached Team ids do not reach the Hub interrupt command.

## Default-worker tasks

`coordinatorTaskAuthority(coordinator)` mints an opaque capability only for the exact live local coordinator. `setWorkerPoolSize()` accepts that capability, clamps the requested target to `maxWorkerCount`, activates newly invited workers, retires idle excess workers, and returns active/idle/busy/queued counts plus a saturation flag. Automatic shrink keeps slot zero and any participant that still anchors a pending review consult active until that review settles. `startDefaultWorkerTask()` accepts the same capability, a caller-supplied branded task-creation key, subject, instructions, and read/write scopes. Before admission, TeamRun raises the target to cover outstanding independent default-worker tasks, then mints a one-shot activation proof for the current coordinator; the Hub derives durable creator identity from that proof, preserves the declared scopes, lazily activates the configured non-delegating worker, and fixes the remaining task policy to the default worker, shared workspace, and configured limits. If a reviewer preset is configured and the task declares mutating scopes, the task freezes a participant-review route and the reviewer is activated before admission. A matching retry uses a fresh proof and returns the Hub-retained task.

Task start, list, watch, cancellation, and terminal wait values carry the frozen `reviewPolicy` and a bounded `reviewResult`. The result is either `{ attemptId, decision: 'accepted' | 'rework' }` from that attempt's durable review record or `null` when it has no decision. An active lease selects its attempt; otherwise the latest settled attempt is selected. Thus a pending task may expose its latest rework decision, but a newly assigned attempt never inherits it. A `none` policy and a participant policy with a null result remain distinct. The projection omits review reasons and older attempt decisions.

`waitForDefaultWorkerTask()` accepts only a task previously admitted through the same coordinator authority. It watches the Team journal until `completed`, `failed`, `cancelled`, or `deleted`, including configured review; completion returns the retained result, while failure preserves its final failed, released, or lease-expired attempt fact. Its signal stops only that local watch and does not cancel, delete, or otherwise mutate the durable task.

`listDefaultWorkerTasks()` returns the compact phase of every non-workflow task admitted through the coordinator authority. `watchDefaultWorkerTasks()` waits for a Team cursor advance and returns the same bounded snapshot with its new cursor; its signal stops only that local watch. A provider watch result that repeats or rewinds the requested Team cursor fails the local wait with `TEAM_RUN_NOT_QUIESCENT` instead of resubmitting the same watch.

`proposeDefaultWorkerTaskOwner()` records or clears an advisory Participant hint on an owned pending task through the same one-shot task-control proof. The hint is durable and revision-fenced, but it confers no task authority; the scheduler still validates the candidate's capabilities, availability, workspace, and budgets before assigning work. These proofs apply only while this current coordinator owns the run; post-release cancellation cleanup uses separate authority.

## Declarative workflow plans

`startWorkflowPlan()` accepts one complete `TeamWorkflowPlan`, validates its task DAG, bounds, result selection, participant-role graph, and exact versioned workflow extensions before Team admission. A missing `channel.viewPolicy` is rejected before participant activation or plan/task persistence. TeamRun uses a fresh current-coordinator activation proof for plan admission and each plan-template task command, so the Hub derives the durable plan actor and task creator. The Hub records the plan in `compiling`, then TeamRun opens or recovers the plan-owned workflow channel, binds each task in dependency order, and marks the plan `ready`. A scheduler ignores workflow tasks until that ready record exists and enforces the plan's parallelism and total-attempt bounds. Repeating the same model-call lineage reuses the plan, channel, and task bindings; a restart can continue an incomplete compilation from those records.

For the compiler-owned channel open, plan channel/task bindings, and plan phase transitions, TeamRun retains a separate one-shot `TeamSystemWorkflowProof` with the exact plan, cursor, revision, manifest, binding, or terminal payload. If a channel opened for a compiling plan cannot bind, TeamRun uses its scoped orphan cleanup proof to close only that unbound channel; a later bound channel is never eligible for this cleanup.

An active custom or remote agent role without a resident activation is prepared through `ctx.teamPlacement.prepareRoles()` after plan admission and before channel creation. Missing placement or routes reject compilation; partial success retains the compiling plan for retry. An unsettled old epoch requires recovery. The compiler does not schedule its partially bound tasks.

`cancelWorkflowTask()` selects an owned plan/template binding and returns exact-task stop progress. `waitForWorkflowPlan()` waits for all bound tasks and reads the Hub’s aggregate completed/failed/cancelled result with only the configured task projection. Cancelling the wait does not cancel the workflow. The local shipped Consumer resolves channel roles to the default coordinator, worker, and configured reviewer Participants and uses the shared workspace by default; a non-shared workflow mode requires its provider and scheduler mode to be explicitly mounted.

## Coordinator objective authority

`tryCoordinatorGoalAuthority(coordinator)` mints a separate opaque capability for the exact local coordinator, or returns `undefined` for an ordinary Agent. `readCoordinatorGoal()` reads its durable objective, and `updateCoordinatorGoal()` sends a compare-and-set edit through the Hub with a private short-lived proof issued from that coordinator's activation lease. Every call revalidates the live Agent, scoped initiator, and durable activation; an edit additionally requires the current open turn to contain a direct v3 human Envelope from this run's human participant on its default channel.

## Single-task cancellation

Task start/list/watch/wait and cancellation results include bounded `cancellation` progress: the requested revision, selected attempt or null for pending work, and whether its lease deadline elapsed. Null means no single-task intent. `cancelDefaultWorkerTask()` accepts pending, review, assigned, or running work while the Team remains active. [Cancellation ownership](../../../.agents/notes/implemented/architecture/2026-09-06-exact-single-task-cancellation.md).

`workerCount: 0` with `maxWorkerCount: 0` creates a coordinator-only Team through the ordinary channel, final-receipt, closure and resume paths. Its handle has no `worker`; delegated worker tasks reject instead of adding capacity.

`members` declares additional eager model participants with unique roles, capabilities and explicit runtime provider, model route, optional preset and output-token limit. These routes are frozen in the Team template and reused on resume; a descriptor mismatch rejects recovery. Workflow execution and reviewer roles resolve against the active roster instead of requiring the default worker. The run handle exposes these identities as `members`; their activations use the same controller and cancellation settlement as the coordinator and worker pool.

## Model Experience

### Coordinator final output

#### What the model sees

The coordinator receives its human input as a durable direct v3 `user/message` with Team provenance. An optional request preset composes its scoped tools and prompt sections before Team-run adds the direct-channel instruction requiring `team_final` for the human-visible result.

#### Token effect

One scoped final-output instruction and one `team_final` tool schema are added to the coordinator's next request. A selected preset owns its additional token effect. Human input and final output remain dynamic channel/session facts.

#### KV Cache effect

The final-output instruction and selected preset are stable for the coordinator activation. Human input and the tool result are dynamic suffix entries.

## Known Limitations and Deferred Work

- Distributed human delivery remains a separate Phase 8 concern. Attachment ingress is handled by Host Team input admission, and review routing is available when a reviewer preset is configured. Crash recovery still requires a persisted provider-specific fence plan.
- This local provider owns only its current process's runs. Unloading removes its source-scoped final-receipt proofs and leaves active durable Teams for a later recovery owner, which must `resume()` before waiting for or settling a final result.
