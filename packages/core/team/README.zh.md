# @clocky/clocky-team

[English](README.md) | 中文

Team 工作系统的 Service Definition。它提供独立的 Team、带 revision 的 goal、participant、activation、channel、envelope、task 和 task-attempt 身份；Team、goal、task 和 channel 记录的解析器；不可变的协议词汇；抽象的 `ctx.teams` 提供方约定；带版本的 channel 适配器注册表；以及类型化的 Team 策略 waterfall。

`TeamRuntime`是抽象类。应加载本地 [`@clocky/clocky-team-hub`](../../team/team-hub/README.zh.md) 提供方，而不是单独加载这个包。Hub 实现持久 Team journal、channel WAL、恢复、成员和任务变更、游标 watch、quiescence 诊断，以及不删除状态的终态 Team 归档；投递、调度和 Agent placement 仍是独立提供方工作。本包不导入 Hub、投递、调度或 storage 实现；可选的 `TeamTelemetryCoordinator` 会观察类型化的 Team/channel feed 与 Session event，但不持有任何 Agent loop。

浏览器安全 consumer 从 `@clocky/clocky-team/types`导入记录类型，并从 `@clocky/clocky-team/schema`导入运行时 parser；包根还会加载 `ctx.teams` Service Definition。

`getChannelAdmission()` 读取持久 endpoint invitation；`acknowledgeChannelInvitation()` 通过当前 activation、authenticated-human 或具名 system proof 接受准确的 manifest fingerprint 与 invitation revision。`expireChannelInvitations()` 只接受 admission Consumer 绑定 cursor 和 clock 的 proof。`ChannelEnvelopeRecord.deliveryIntents` 在接纳时固定 recipient 身份。[Channel admission Consumer](../../team/team-channel-admission/README.zh.md)拥有 dispatch 等待和 deadline recovery。

`TeamResourceBudget.maxChildTeams` 是累计后代数量上限。`taskChildTeamReservation()` 统计每个已接纳 child 及其冻结的后代额度，包括终态和已删除任务；admission 与 replay 均检查该上限。

`reserveActivation()` 与 `releaseActivationReservation()` 要求准确的 controller 启动 proof。provider 启动未返回句柄时，`ParticipantSnapshot.activationReservation` 仍持久保留；`ActivationBindingSnapshot.reservationId` 把发布的 epoch 关联到唯一 admission。`liveActivationCapacity()` 依据这些记录和未结算 child 额度检查 `TeamResourceBudget.maxLiveActivations`。

成员详情通过`team.member.inspect`读取准确身份、角色、非敏感 placement 信息及一页 capability。续页使用已观察的 Team cursor，冲突后需要刷新。页面不包含 grant、启动配置或 attempt 统计，并受 Hub 响应字节额度限制。

## Provider contract

`getArtifact()`是 provider-owned 的准确 lookup，用于读取一个可见且无歧义的 artifact reference；Host 和 SDK artifact read 会使用它，而不会 materialize 完整 Team snapshot。Private 或 ambiguous reference 会按 absent 处理，而返回的 reference 仍保留其 provider 与 provenance 供 artifact service 使用。

Authority grant 可以携带可选的 placement restriction。Task creator 不能准入显式或 template-resolved placement 超出该 grant 的 Participant、role、provider、preset 或 model；省略 placement 时从 Team product template 解析一次并随 task 持久化。

产品读取使用独立的有界 page method：`listTeamsPage()`、`listParticipantsPage()`、`listTasksPage()`和`readChannelPage()`接受 exclusive cursor 与正整数 limit，最多返回该页并在还有内容时给出可选的 `nextCursor`。Team discovery 使用 opaque `TeamDiscoveryCursor`，以 `scanned` 报告包含跳过名称的工作量；空页也可能有 continuation。从 `-1` 开始，遇到 `TEAM_DISCOVERY_CURSOR_EXPIRED` 时从此重扫。participant/task cursor 仍指向 durable provider order，channel cursor 仍是 WAL sequence。本地 Hub 会以配置的 recovery read size 限制每个请求页。`expireSchedulerChannelDeliveries()`只接受准确的 `TeamSystemSchedulerChannelProof`；其 scheduler scope 会绑定 Team/channel cursor、clock observation 与有界 batch，再追加 TTL expiry record，且不会推进 receipt high-water。`readChannelSummarySource()`验证当前协调者或经过认证的人类，选择对全频道可见的有界来源范围。`summarizeChannel()`要求该请求者及来自规范[显式摘要 Consumer](../../team/team-channel-summary/README.zh.md) 的精确证明。JSON 输入绑定来源 id 与指纹、范围、文本、策略、幂等键和游标；provider 在追加前复核身份与权威来源，并在重放时验证来源关系。证明不进入持久化记录。旧的 full `listTeams()`和`readChannel()`继续作为 scheduler 与 recovery scan 的 provider-owned seam，不作为产品 transport method。

Participant 可以在先前 epoch 成为 `offline` 后保留多个 epoch，但每个 epoch 使用相同 Session，且最多一个 epoch 保持 resident。`postChannelEnvelope()`只接受 JSON cursor/retry/draft 字段和一个不透明运行时 actor。activation proof 派生当前 sender；authenticated-human proof 派生 active product human sender；已注册的 system proof 只派生 TeamRun human input 或 scheduler-owned assignment/review post。task-assignment 与 review-request draft 会拒绝 activation proof，任何 post 都不接受 caller-selected sender、activation 或 Session。`resolveTaskReview()`会从 activation 或 authenticated-human proof 派生 reviewer，不接受 Team 或 Participant identity。独立的 `TeamSystemTaskReviewProof`只允许 scheduler 在验证准确 task、channel、request、response、decision 和 reason 后修复一条持久 consult response。adapter-owned final post 由严格的、只含 JSON 的 `ChannelFinalPostInput` channel、retry-key 和 text 字段，以及仅限运行时的 `ChannelFinalPostRequest`中的不透明 `TeamActorProof`组成；它不接受 sender 或 activation 字段。`openActivationActorProofIssuer()`会在创建可撤销 proof lease 时校验并冻结 binding；provider 使用受保护的 `requireActivationActorProof()`派生该 binding，并以 `TEAM_ACTOR_PROOF_INVALID`拒绝 forged、foreign 或 revoked proof。`ackChannelEnvelope()`在目标 flush 后记录 recipient admission；重复调用会返回原始持久 receipt，而不会再次追加 channel projection 和 delivery intent。它返回临时 Hub-issued claim；该派生 recipient 已持久确认 Envelope 时返回 `undefined`。已定义 claim 既不保留模型 turn，也不承诺 exactly-once 投递。成功的 claim 不写入持久记录，也没有 claim identifier 或 settlement 操作。`listChannelPendingDeliveries()`为一个 recipient 返回有界、仅供发现的页面；其 source channel-WAL cursor 从不使用 receipt high-water，每个发现的 Envelope 在 admission 前仍需要 delivery claim。`watchTeam()`和`watchChannel()`接受可选的本地 `AbortSignal`；提供方会在严格 JSON 解析前省略它，cancellation 不会改变 wire 数据或持久状态。root Team 的 `depth: 0`；nested Team 同时命名 `parentTeamId` 和 `parentTaskId`，并携带由提供方解析的 `depth` 与不可变 `maxTeamDepth`。Team id 是提供方创建的专属品牌值；`SessionId`绝不是 Team id。导出的 Zod 解析器在文件、队列、进程或 wire 边界验证 id、封闭生命周期值、只含 JSON 的数据、Team/goal/task 读取模型、task lease 和已结算 attempt、activation binding、envelope、manifest、channel 记录、delivery claim、task-start claim、pending-delivery page 和策略载荷。纯生命周期检查会在提供方追加记录前拒绝无效的初始、回退和终止后转换。

`bindActivation()`、`updateActivationStatus()`、`fenceActivation()`与`quiesceActivation()`会将 JSON-only compare-and-set field 与 `TeamSystemActivationProof`分开。`team-activation-controller`只能解析一条准确的 bind、status、fence 或 quiesce scope；`team-activation-recovery`只能解析已本地 quiesce epoch 的一条 retained wake-cleanup retry。provider 会先解析 source 选择 Team，再在 lock 内重新解析并匹配 current binding，之后才执行 policy 或 journal append；持久 binding 与 record 都不保留 proof。

system final-receipt source 会持有自己的不透明 `TeamSystemFinalReceiptProof`对象，并通过 `registerSystemFinalReceiptProofSource()`注册 resolver。runtime 只返回经过校验和冻结的 Team/channel/human/coordinator scope，在该 source unload 时使其 proof 失效，且不公开通用的 human 或 system proof issuer。本地 `team-run` source 仅为其当前本地保留的默认 topology 使用该 authority；提供方仍须在 policy 或 receipt append 前验证 active 的双人 direct-v3 channel，以及仅面向 scoped human 的非空 coordinator `final`。因此 receipt request 通过 activation 或 source-scoped final-receipt proof，而不是调用方指定的 recipient。

Closure command 将只含 JSON 的 `TeamClosureInput`/`TeamCompleteInput`字段与仅在运行时存在的 `TeamClosureAuthority`分开。activation proof 会派生当前 active participant attribution。注册的 system source 会解析封闭的 `TeamSystemClosureScope`；本地 `team-run` source 只能授权其准确默认 topology 的 completion、cancellation 或发布前 creation failure。provider 会在持有相关 Team 和 channel serializer 时重新解析 proof，再执行 replay、policy 或 durable acceptance；它只会持久化派生出的 `TeamClosureActor`，绝不会持久化 proof 或 source scope。

`transitionTeamPhase()`同样接收只含 JSON 的字段和不透明 `TeamSystemPhaseProof`。其封闭 system scope 授权 `team-run`将一支 stalled Team 恢复为 `active`，在本地 release 前将一条已由 human receipt 的默认 final 从 `active`置为`quiescing`，以及授权 `team-scheduler-dag`以准确 reason 将一支 active Team 置为 `stalled`。finalization scope 会绑定 final channel、Envelope、human、coordinator 与 Team cursor；provider 会在其 serializer 内连同 final channel 校验这些事实，然后才执行 close policy 或 journal acceptance。不再保留通用 lifecycle actor 或 raw phase transition。

终态 channel 与 Team-journal compaction 也将只含 JSON 的 prefix 字段与 `TeamSystemMaintenanceProof`分开。scheduler 唯一的 scope 绑定准确 Team/channel、观察 cursor 和 `throughSequence`；provider 会在其 serializer 内再次解析 proof，然后才执行 policy、audit repair、checkpoint write 或不可逆 source compaction。历史 `TeamClosureActor`仍只作为 durable attribution，绝不授权 maintenance ingress。

Soft interrupt 也按 owner 分开。`team-run`只能通过 `TeamSystemInterruptProof`请求其当前默认 human-to-coordinator interrupt；scope 会派生两个 participant 和 channel topology。activation-bound Link 只有携带私有 `TeamActorProof`才能列出或确认 interrupt，provider 会从中派生准确 target binding。任何 interrupt request、pending read 或 acknowledgement 都不接受 caller-selected participant、activation、Session 或 provider 字段。

`requestParticipantInterrupt()`解析 active agent 的 idle 或 running binding，记录其精确的 activation/Session/provider target，并执行 `interrupt` policy。只有该 target 可以列出并幂等确认请求；它既不取消 Team，也不结算 turn。`upsertHumanAction()`和`resolveHumanAction()`只接收 Team/cursor field 与 `TeamSystemHumanActionProof`。Host API proxy 会保留准确的 verified pending action 或 terminal resolution scope；provider 会在 Team serializer 内重新解析它，以派生 durable action、policy actor 与 timestamp；不再拥有该 entry 的 Host 会 fail closed。settled action 会保留 request detail 与 outcome，因此 Team read 在重启后仍可恢复。`recordUsage()`接收 current activation proof 与 JSON-only provider/model fact；provider 会在 Team serializer 内重新验证 binding，并在 parent-charge repair、replay、policy 或持久 accounting 前派生 Team、Participant、Session 与 timestamp。它是 provider 用来写入幂等 Session turn/step usage sample 以及持久 Team subtree token/turn/cost aggregate 的 seam。Child Team 会先提交本地 sample，再传播幂等的 parent charge；未结算的 charge 会阻止新的 child work，并在后续 admission 前修复。Hub 可以在 Team creation 时快照 provider/model `usageRates`，为缺少 provider cost 的 sample 计算 pricing；显式 sample cost 始终优先。`inspectQuiescence()`为 completion policy 提供只读的 active task、live activation、open channel 和 pending human action 诊断。Typed cancellation request 会在 resource teardown 前持久化；其 `cancellation` projection 将已接纳的 stop 与终态 `closure` 区分开。

`TeamRootCreateInput`接收必填的 goal seed、typed Team resource budget 和可选的不可变 authority grant。其运行时 request 必须携带 `TeamSystemRootCreationProof`；当前 `team-run` source 会在 Team identity 存在前绑定完整 root payload，provider 会在 `register` policy 后以及打开新 stream 后、首次 append 前重新验证该 proof。proof-owned root 会在 Team record、snapshot 与 checkpoint 中保留不含 secret 的系统 `createdBy` provenance。`TeamChildCreateInput`同样是 JSON-only，但它的运行时 request 必须携带包含完整 child payload 和一条 observed parent cursor 的 `TeamSystemChildCreationProof`。唯一可接受的 source name 是 `team-child-delegation`；shipped composition 会在 parent-task delegation consumer 拥有它之前刻意不挂载该 source，因此 raw child creation 会 fail closed。provider 会在 parent repair 前、在 parent lock 内、register policy 后以及打开 child stream 后解析 proof。hierarchy data 或 parent task 都不能重建该 proof，child journal 也不会保留可复用 credential。Child Team 与 Participant 只能收窄 parent 的 operation、workspace、scope 和 typed budget grant。`TeamSnapshot`和`TeamStateSnapshot`公开当前 `TeamGoalSnapshot`；它包含所属 Team id、goal-local revision、objective、phase、可选 blocker 以及 goal-specific budget。`updateTeamGoal()`和`transitionTeamGoalPhase()`接收只含 JSON 的 goal 字段和一个不透明 `TeamActorProof`；提供方会在 Team lock 内重新校验当前 human 或 activation authority，并在 commit 前派生 policy participant。更新会在不改变 phase 的情况下修改 objective 文本和／或 goal budget；转换使用同一 fence，`blocked`必须带 blocker，`active`、`paused`和终止的 `complete`不带 blocker。Team failure 和 cancellation 仍是 Team lifecycle fact。

`archiveTeam()`将 JSON-only `TeamArchiveInput`与 runtime-only system 或 authenticated-human proof 分开。`team-run`可以在结算 own Team 后保留一条 in-memory terminal owner；其准确 system scope 包含 Team 与 observed cursor。authenticated human proof 将相同完整 input 绑定到拥有 `close` authority 的一个 active human Participant，因此 detached 或 restart 后的终态 Team 仍可归档，而无需重建 TeamRun owner。provider 会在加载 Team 前、在 Team lock 内（包括已经归档的 idempotent read）以及 `close` policy 后、追加未改变的 `team/archived` record 前再次解析 proof。Team id、archived snapshot、roster data 或 restart 都不能重建任一 proof；proof 绝不写入 journal、checkpoint 或 wire request。

Participant 邀请会冻结去重后的 capability 列表，供后续 scheduler 判断资格。`ParticipantInviteInput` 与 `ParticipantPhaseTransitionInput` 只包含 JSON 字段；受信 topology source 使用 `TeamSystemTopologyProof`，authenticated product call 则为非 human participant 的 invite 与 phase mutation 使用 `TeamHumanActorProof`。human participant 的创建仍仅限受信 topology/bootstrap source，Host/SDK wire 不提供 owner。`team-run` source 只能在发布 Run 前签发 bootstrap invite/phase scope，在发布后为已声明 worker 签发 `provisioning` 到 `active` 的 scope，并为惰性 provision 的 reviewer 签发 invite/phase scope。同一 proof 只能打开首个 direct-v3 human/coordinator channel。通用的非 workflow channel open 与普通 close 都需要准确的 `TeamSystemChannelLifecycleProof`；其 runtime-only dispatch marker 选择通用途径，而已注册 source 会绑定完整 JSON payload。provider 会在 topology 或 human scope 的 policy 前解析它们，并在 Team serializer 内再次解析后才追加记录，因此 raw participant ingress 会 fail closed。Task 创建会冻结祖先 task、所需 capability、priority、文件系统 scope、workspace mode、budget、封闭的 review route（`none`或一个 participant）以及 `maxAttempts`。每次 Task 创建都携带含幂等 key 的 retry `createCommand` 和 runtime proof。coordinator proof 派生 activation creator；authenticated-human proof 绑定完整 parsed input，并派生只含 Team 与 Participant id 的 durable human creator。provider 会在 replay、policy 或 append 前重新验证 proof，wire input 不包含 creator identity 或 proof。workflow-plan admission 同样使用 coordinator proof 并派生 durable actor。Task 可以保留 advisory `proposedOwnerId`；它只是 scheduler hint，绝不会授予 authority。task 要么没有 lease，要么为一个 `assigned` 或 `running` attempt 保留当前 lease。assigned lease 没有 start time，running lease 必须有 start time。其 `attemptCount` 等于已结算 attempt history 加上该 lease；其中 task-local ordinal 和 id 永不复用。lease 会保留其 assignment revision，并可保留一个已附加的 wake channel。agent-owned lease 保留 `ActivationId`；human 和 service lease 省略它。owner 操作会重复该精确 epoch，因此 stale residency 不能续期或结算较新的 lease。

`assignTask()`创建 lease，并可保留一个已附加的 wake channel；`startTaskAttempt()`要求精确的 revision、attempt id、Participant 和适用的 activation。`heartbeatTaskAttempt()`和`settleTaskAttempt()`接受一个不透明 `TeamActorProof`以及只含 JSON 的 task、attempt 和 revision identity；settlement 额外只接受 `released`、`failed`、`completed`或`cancelled`。在 Team/task serializer 内，提供方会解析并重新校验该 binding，然后派生 Team、Participant、activation 和 Session，再续期或结算 lease。`claimTaskAttemptStart()`只接受一个不透明 `TeamActorProof`以及只含 JSON 的 task、attempt、assignment-revision、wake-channel 和已接收 task-Envelope identity。在 Team/channel serializer 内，提供方会解析并重新校验该 binding，派生 Team、Participant、activation 和 Session，然后绑定 assignment delivery；对同一当前 claim 的重复调用会返回 running task，而不会再写入一条 journal record。`expireTaskAttempt()`在 deadline 后要求 revision 和 attempt id。completed attempt 保留 summary，failed attempt 保留 code 和 message；artifact reference 不属于此定义。`none` review route 可以直接完成已接收的 attempt；participant route 会为每个 completed attempt 保留 reviewer decision，包括非空 reason 以及所选 `completed`或`pending` phase。只有 task 处于 `review`时，它才保留恰好一条未解决的 completed attempt。`resolveTaskReview()`要求配置的 reviewing Participant，并通过 `task-mutate` policy 记录该决定。`proposeTaskOwner()`只会修改无 lease pending task 的 advisory proposal，验证被命名的 Participant 属于该 Team；如果该 Participant 其他方面不合格，scheduler 会继续选择其他候选者。`deleteTask()`会拒绝等待 review 的 task，因此不能丢弃未解决的 completed attempt。`updateTaskDetails()`只在提供方验证没有当前 lease 后修改 instructions 和 dependencies；它不能重写 task phase、scheduler facts 或 attempt state。

Integration task 会在同一条 task record 中加入不可变的 source task/attempt、provider、target、expected target revision，以及 proposal 或 merge mode。其 completed attempt 必须保留与 task 相匹配的 integration result；integrated result 包含最终 target version，conflict result 包含冲突路径，最终 verification 与 artifact manifest 保留在普通 durable attempt result 中。Hub 会在接纳 task 前验证 source attempt 并执行 `workspace-integrate` policy，然后在 task policy 后、task CAS append 前再次验证 result。Workspace provider 仍拥有 bytes 和 Git operation；Team record 拥有 integration task 的 authorization 与 outcome。

direct attempt start 现在从`TeamActorProof`派生 Team、participant 与 activation；task details edit 与 tombstone 则要求 current coordinator proof。这些 request 都不接受 caller-selected owner、participant 或 activation identity，并且每条路径都会在`task-mutate` policy 后、append 前重新验证 proof。

`assignTask()`与`expireTaskAttempt()`接收 JSON-only task/lease field 和 `TeamSystemTaskLeaseProof`。只有 `team-scheduler-dag`可以解析一条准确的 selected assignment 或 elapsed attempt；provider 会在 parent-charge repair 前重新解析该 scope，并在 policy 或 commit 前于 Team 与已附加 wake-channel serializer 内再次解析。scheduler 会在 call 结束后撤销 proof，并在 assignment 未提交时关闭刚打开的 wake channel。

scheduler review、wake channel 与 delivery-expiry lifecycle 使用独立的 `TeamSystemSchedulerChannelProof`。其封闭 scope 会为准确的 completed attempt 与 idle reviewer binding 打开一条 participant-review consult channel，为准确的 pending task 与 idle activation 打开一条 self-addressed task-assignment wake channel，以固定 diagnostic 关闭一条未被 lease 引用的 orphan wake channel，或以准确 Team/channel cursor 与 scheduler clock observation 使一条有界 due-delivery prefix 失效。provider 会在 repair 前验证 source scope，并在 Team/channel serializer 内、policy、channel creation、attachment、close 或 expiry append 前再次验证；任何被当前 task lease 引用的 wake channel 都不属于 cleanup。此类 proof 不会分配 task 或 post Envelope。

workflow compiler mutation 使用 `TeamSystemWorkflowProof`。命名 `workflowPlanId`的 channel open 需要其 compiling plan revision、current coordinator binding 与准确 TeamRun scope；plan channel/task binding 以及 ready 或 terminal phase 同样需要对应 proof。只有在 compiling plan 尚未绑定该 channel 时，attached workflow channel 才能通过独立的 orphan-cleanup command 关闭，因此 generic channel authority 无法终结 plan 的 bound channel。

current-coordinator default-worker owner proposal 与 task cancellation 使用 `TeamSystemTaskControlProof`。source 会绑定准确 coordinator、task revision 以及 proposal 或 cancellation payload；provider 会在 Team lock 内重新解析它，并在 policy 或 append 前验证 task 的 durable creator provenance。release 后的 cancellation cleanup 使用独立的 `TeamSystemCancellationCleanupProof`，它绑定一条 durable cancellation identity 及一个 pending task 或 active channel。completion cleanup 使用 `TeamSystemFinalizationCleanupProof`，它绑定一条已由 human receipt 的 final、默认 human/coordinator topology 和一个 active channel。provider 会在 policy 或 durable append 前重新验证两类 proof 的准确 cursor 与 durable fact；任一 proof 都不能授权通用 task 或 channel mutation。

activation-bound Link 会私有地持有 `TeamActorProof` lease。其 receipt input 只包含 channel、Envelope 与 observed-cursor 字段；提供方会在持有 Team/channel serializer 时重新校验 proof，并在 receipt policy 或 WAL admission 前派生 recipient。heartbeat input 只包含`taskId`、`attemptId`和`expectedRevision`；settlement 额外携带其 typed outcome。提供方会先解析 proof 来选择 Team serializer，并在持有 Team lock 时重新校验，再派生 Team、Participant、activation、Session 与精确的当前 lease owner。普通 Link `post()`和 review request 保持各自类型化的 contract，Team-closure authority 不属于此 receipt boundary。

提供方调用 `registerAdapter()`，以精确的 `(type, version)` 身份提供一个同步、纯粹的 channel 适配器。注册由 effect 管理，且对 HMR 安全。channel manifest 会冻结该身份及其 participant，而 channel WAL 单独存储生命周期边。

提供方调用 `registerPolicy(hook, policy)`，围绕 `register`、`invite`、`activate`、`channel-open`、`send`、human-action、usage、`dispatch`、goal 变更、task 变更／分配、中断、workspace 分配／integration 和关闭操作组合治理。允许操作的策略调用 `next()`；策略返回结构化拒绝而不委托。`authorize()` 返回组合后的决定。提供方只在持久提交点后发出 `team/changed`、`goal/changed`、workflow-plan 和带身份的 `channel/changed` 通知；观察者失败会被包含并记录。`readAudit()`会按源游标读取由 provider 为 Team journal 或已附加 channel WAL 维护的有界 projection，但不会将其变为权威状态。`compactChannel()`与`compactTeam()`是 provider-owned maintenance command，实现必须保留 source cursor，并在移除 history 前分别校验 terminal-channel 或 Team-journal watermark。压缩后的 channel snapshot 与 audit page 可以公开 first retained cursor，让 consumer 无需猜测 retained boundary 就能恢复。`getMetrics()`会在现有进程内计数器之外，提供 compaction、checkpoint failure、audit projection repair 与 failure counter。

`TeamTelemetryCoordinator`是这些 feed 的可选 capture Consumer。它发出 detached 的 Team journal、channel WAL、Session model/tool span 与 lifecycle record，并把已知的 Team、Participant、Activation、Channel、Envelope、Task、Attempt、Session、provider、model、trace、causation 与 correlation identity 复制到 primitive attribute。`team-telemetry/record` waterfall 是部署方的 redaction/enrichment 扩展点；sink 的 batching、retry、loss、export 和 alert threshold 仍由 provider 负责。Coordinator 会隔离 observer 与 sink failure，保证 telemetry 不会中断 authoritative append 或 model loop，并在 backend shutdown 前转发 Session flush hint。

该定义也拥有只含 JSON 的 `TeamWorkflowPlan` 词汇。提供方可以准入一个完整 plan，通过 compare-and-set revision 绑定 task template 与 workflow channel，并将其从 `compiling` 推进到 `ready` 或终态 projection。Plan-local task 和 channel identity 与 Team task、channel id 分离；consumer 仍负责在 admission 前解析 participant role 和 versioned graph extension。

Channel snapshot 可以公开 `replayWatermark`，即最早仍 pending 的 recipient Envelope 之前可安全跳过的最高 source cursor。Link reconnect 会从这个 durable boundary 之后开始；terminal-channel compaction 在删除 source history 前必须通过同一个 watermark 与 pending-delivery 检查。

Local Hub 的 metrics 会在现有 counter 之外提供 pending-delivery depth、active activation/task count、stalled-Team count、replay lag、最近一次 task-attempt latency、最近一次 receipt latency、workspace-conflict count，以及累计的 task/receipt latency histogram。Histogram 使用固定的 Team protocol boundary 和 cumulative positive-infinity bucket。这些值是 operational snapshot，不会授权或拒绝 business mutation。

`admitTeamFinalResult()`接收准确的 final Envelope、WAL sequence、内容 fingerprint、Team-scoped retry key 和 `TeamSystemFinalReceiptProof`。Provider 从 proof 与 Team membership 派生 human recipient 和 durable owner。其 `TeamFinalAdmission`记录封闭的 `team-run-result` sink 独立接纳结果的事实，然后才允许 system final receipt；它不授予 principal inbox、display 或一般 human mutation 权限。相同 retry 返回原始 admission，另一个 key 或变化的 selection 会被拒绝。Admission 及其引用的 WAL 内容会保留整个 Team lifetime。

`ActivationBindingSnapshot.fencedAt` 记录 provider 已确认终止、但 closure-owned allocation 尚未结算的事实；该字段不可变，不代表完整 quiescence。`quiescedAt` 仍要求 allocation 已释放且 task lease 已结算。`requireSystemClosureDriverProof()` 只解析有效的 runtime token；consumer 执行动作前还必须核对准确的持久 intent、Team cursor 与资源 epoch。Controller closure-stall scope 绑定该 intent identity 与 epoch，不允许 resume、replacement 或创建新的 closure。

`getTeamSelection()`是独立的首次选择只读投影，返回有界显示文本、准确 coordinator binding、生命周期和集合计数，不包含历史数组。Host 提供`team.selection`，TypeScript 与 Python SDK 提供`team/selection`。需要完整权威回放状态的 consumer 仍显式调用`getTeam()`。 `includeMetadata: true`仅在完整响应仍符合相同字节上限时附带准确目标、预算和用量；超限返回明确的 unavailable 状态，保留轻量选择结果。待处理人工操作计数与取消原因文本仍是有界显示数据。

`getMemberSession()`解析指定成员最后一个已发布的 Session 绑定，包括离线历史，不触发 activation 副作用。响应不包含 supervisor 配置，并受 Hub 的`maxSelectionBytes`限制。Host 提供`team.member.session`，SDK client 使用`team/member-session`。

`getHumanAction()`按 Team/action 身份读取一个当前持久操作，并受`maxSelectionBytes`限制。缺失或超限时明确失败，不回退到完整状态。Host `team.action.read`和 SDK `team/action-read`保留这一选择；读取不会接纳回答。

`browse()`在整页字节上限内返回具名的任务、成员和工作流摘要，与完整记录 API 分开。显示文本前缀明确标记截断，id 与协议角色保持准确；角色超出整行预算时明确拒绝。省略的行数限制由 provider 配置解析。Host 使用`team.browse`，TS/Python SDK 使用`team/browse`。Ordinal 前缀工作计入`scanned`；冷 hydration 仍在内部执行。

`inspectTask()`选择`record`、`attempts`或`reviews`。`record`省略两类历史数组并返回计数；历史页按数组下标续读，可用`expectedRevision`锁定任务版本。Hub 对完整结果应用`recoveryPageSize`与`maxSelectionBytes`。单个记录超限时明确拒绝，历史页仍可独立读取。任务结果、子团队结果和 integration 中的私有产物引用不会返回。Host 路由为`team.task.inspect`，TS/Python SDK 路由为`team/task-inspect`。

`inspectWorkflowPlan()`返回当前元数据和一页锁定版本的任务/依赖引用，省略说明、协议图和结果正文。整份响应受`maxSelectionBytes`限制，`scanned`报告模板和绑定查找工作量。Host 使用`team.workflow.plan.inspect`，TS/Python SDK 使用`team/workflow-plan-inspect`；内部完整读取仍显式调用`getWorkflowPlan()`。

## Model Experience

### Team definition

#### What the model sees

`ctx.teams` 不注册工具、提示词、模型输入或模型输出。任何模型可见的 Team 投影由提供方或消费方负责。

零。

本包不影响缓存复用。

## Known Limitations and Deferred Work

- `clocky-team`是 Service Definition，不是提供方；使用 `clocky-team-hub` 获取本地持久 Team journal、channel WAL、恢复、检查点和创建时限额执行。
- 调度、远端 Link、远端 reconnect transport 和产品 API 仍位于该定义与当前本地 Hub 之外。如果这些能力没有被组合，provider 可以显式拒绝可选的持久 interaction 与 usage 方法。

### 单任务取消

`cancelTask()`保留以 revision 为 fence 的单任务 intent；`TeamTaskSnapshot.cancellation`标识其精确工作。Live attempt 要等 owner acknowledgement 或 activation quiescence，以及 allocation 释放后才能进入终态。Lease 期限经过不会重新开放被取消的 attempt。 [取消归属](../../../.agents/notes/implemented/architecture/2026-09-06-exact-single-task-cancellation.zh.md).
