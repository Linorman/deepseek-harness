# @clocky/clocky-team

English | [中文](README.zh.md)

Service Definition for the Team work system. It provides independent Team, revisioned goal, participant, activation, channel, envelope, task, and task-attempt identities; parsers for Team, goal, task, and channel records; immutable protocol vocabulary; the abstract `ctx.teams` provider contract; a versioned channel-adapter registry; and typed Team policy waterfalls.

`TeamRuntime` is abstract. Load the local [`@clocky/clocky-team-hub`](../../team/team-hub/README.md) provider rather than this package by itself. The Hub implements durable Team journals, channel WALs, recovery, roster and task mutations, cursor watches, quiescence diagnostics, and terminal-Team archival without deleting its state; delivery, scheduling, and Agent placement remain separate provider work. This package imports no Hub, delivery, scheduling, or storage implementation. Its optional `TeamTelemetryCoordinator` observes the typed Team/channel feeds and Session events without owning any Agent loop.

Browser-safe consumers import record types from `@clocky/clocky-team/types` and runtime parsers from `@clocky/clocky-team/schema`; the package root additionally loads the `ctx.teams` Service Definition.

`getChannelAdmission()` reads durable endpoint invitations; `acknowledgeChannelInvitation()` accepts an exact manifest fingerprint and invitation revision through current activation, authenticated-human, or named system proofs. `expireChannelInvitations()` accepts only the admission Consumer’s cursor- and clock-bound proof. `ChannelEnvelopeRecord.deliveryIntents` fixes recipient identities at admission. The [channel admission Consumer](../../team/team-channel-admission/README.md) owns dispatch waits and deadline recovery.

`TeamResourceBudget.maxChildTeams` is a lifetime descendant ceiling. `taskChildTeamReservation()` counts each accepted child plus its frozen descendant allowance, including terminal and deleted tasks; the ceiling is checked during admission and replay.

`reserveActivation()` and `releaseActivationReservation()` require exact controller startup proofs. `ParticipantSnapshot.activationReservation` survives a provider start without a returned handle; `ActivationBindingSnapshot.reservationId` links a published epoch to its unique admission. `liveActivationCapacity()` counts those records plus unresolved child allowances against `TeamResourceBudget.maxLiveActivations`.

Member details read exact identity, role and non-secret placement hints plus one capability page through `team.member.inspect`. Continuation uses the observed Team cursor; a conflict requires refresh. The page never includes grants, startup configuration or attempt statistics, and remains subject to the Hub response byte allowance.

## Provider contract

`getArtifact()` is a provider-owned exact lookup for one visible, unambiguous artifact reference; Host and SDK artifact reads use it instead of materializing a full Team snapshot. Private or ambiguous references resolve as absent, while the returned reference retains its provider and provenance for the artifact service.

Authority grants may carry optional placement restrictions. A task creator cannot admit a task whose explicit or template-resolved placement names a Participant, role, provider, preset, or model outside that grant; omitted placement is resolved from the Team product template once and persisted on the task.

Product reads use separate bounded page methods: `listTeamsPage()`, `listParticipantsPage()`, `listTasksPage()`, and `readChannelPage()` accept an exclusive cursor plus a positive limit and return at most that page with an optional `nextCursor`. Team discovery uses an opaque `TeamDiscoveryCursor` and reports `scanned` work units, including skipped names; empty pages can carry a continuation. Start at `-1` and restart there after `TEAM_DISCOVERY_CURSOR_EXPIRED`. Participant/task cursors retain durable provider order; channel cursors remain WAL sequences. The local Hub caps each requested page by its configured recovery read size. `expireSchedulerChannelDeliveries()` accepts only an exact `TeamSystemSchedulerChannelProof`; its scheduler scope binds Team/channel cursors, a clock observation, and a bounded batch before it appends TTL expiry records without advancing receipt high-water. `readChannelSummarySource()` authorizes a current coordinator or authenticated human and selects a bounded, channel-wide source range. `summarizeChannel()` requires that requester plus an exact proof from the canonical [explicit summary Consumer](../../team/team-channel-summary/README.md). Its JSON input binds source ids and fingerprint, range, text, policy, retry key and cursor; the provider rechecks identity and the authoritative source before append and verifies provenance during replay. Proofs never enter durable records. The legacy full `listTeams()` and `readChannel()` methods remain provider-owned seams for scheduler and recovery scans, not product transport methods.

`TeamRuntime` declares the common Team, goal, participant, activation, task, channel, authenticated Envelope-admission, recipient-receipt, delivery-claim, task-start-claim, and pending-delivery-page operations; a provider implements their durable storage and recovery. `bindActivation()` records one provider-owned epoch with its exact Session and provider name, `updateActivationStatus()` advances that epoch, and `getActivation()` reads it by `ActivationId`. An active local-agent or remote-agent Participant may retain multiple epochs after prior epochs become `offline`, but every epoch uses the same Session and only one epoch may remain resident. `postChannelEnvelope()` accepts only JSON cursor/retry/draft fields plus an opaque runtime actor. An activation proof derives the current sender; an authenticated-human proof derives an active product human sender; registered system proofs derive only TeamRun human input or scheduler-owned assignment/review posts. Task-assignment and review-request drafts reject activation proofs, and no post accepts a caller-selected sender, activation, or Session. `resolveTaskReview()` derives the reviewer from an activation or authenticated-human proof and accepts no Team or Participant identity. A separate `TeamSystemTaskReviewProof` lets only the scheduler recover one exact durable consult response after it verifies the task, channel, request, response, decision, and reason. An adapter-owned final post carries strict JSON-only `ChannelFinalPostInput` channel, retry-key, and text fields plus an opaque `TeamActorProof` in its runtime-only `ChannelFinalPostRequest`; it accepts no sender or activation fields. `openActivationActorProofIssuer()` validates and freezes a binding when it mints a revocable proof lease, while providers use protected `requireActivationActorProof()` to derive that binding and reject a forged, foreign, or revoked proof with `TEAM_ACTOR_PROOF_INVALID`. `ackChannelEnvelope()` accepts only channel, Envelope, and observed-cursor fields plus a runtime `ChannelEnvelopeReceiptActor`; it accepts no caller-selected recipient, activation, or Session. An activation `TeamActorProof` derives its current active channel recipient after binding revalidation, while a system proof is limited to an exact registered final-receipt scope. A duplicate returns the original durable receipt without another WAL append. `claimChannelDelivery()` takes an opaque `TeamActorProof` plus only JSON-only channel and Envelope identities. Under the Team/channel serializers, a provider resolves and revalidates the proof's exact deliverable binding, then derives the Team, activation, Session, recipient, current channel projection, and delivery intent. It returns an ephemeral Hub-issued claim, or `undefined` when that derived recipient already durably acknowledged the Envelope. A defined claim neither reserves a model turn nor promises exactly-once delivery. A successful claim writes no durable record and has no claim identifier or settlement operation. `listChannelPendingDeliveries()` returns a bounded discovery-only page for one recipient; its source channel-WAL cursors never use receipt high-water, and each discovered Envelope still requires a delivery claim before admission. `watchTeam()` and `watchChannel()` accept an optional local `AbortSignal`; providers omit it before strict JSON parsing, and cancellation changes neither wire data nor durable state. A root Team has `depth: 0`; a nested Team names both `parentTeamId` and `parentTaskId`, then carries the provider-resolved `depth` and immutable `maxTeamDepth`. Team ids are provider-minted values under a dedicated brand; a `SessionId` is never a Team id. The exported Zod parsers validate ids, closed lifecycle values, JSON-only data, Team/goal/task read models, task leases and settled attempts, activation bindings, envelopes, manifests, channel records, delivery claims, task-start claims, pending-delivery pages, and policy payloads at file, queue, process, or wire boundaries. Pure lifecycle checks reject invalid initial, backward, and terminal transitions before a provider appends its record.

`bindActivation()`, `updateActivationStatus()`, `fenceActivation()`, and `quiesceActivation()` split JSON-only compare-and-set fields from `TeamSystemActivationProof`. `team-activation-controller` may resolve only one exact bind, status, fence, or quiesce scope; `team-activation-recovery` may resolve only a retained wake-cleanup retry for an already locally quiesced epoch. A provider resolves the source once to select the Team and again under its lock to match the current binding before policy or a journal append; neither durable bindings nor records retain the proof.

System final-receipt sources retain their own opaque `TeamSystemFinalReceiptProof` objects and register a resolver with `registerSystemFinalReceiptProofSource()`. The runtime returns only a validated frozen Team/channel/human/coordinator scope, invalidates that source's proofs when it unloads, and exposes no generic human or system proof issuer. The local `team-run` source uses this authority only for its current locally retained default topology; a provider must still verify an active two-member direct-v3 channel and a nonempty coordinator `final` addressed solely to the scoped human before policy or receipt append. Receipt requests therefore use an activation or source-scoped final-receipt proof rather than a caller-selected recipient.

Closure commands split JSON-only `TeamClosureInput`/`TeamCompleteInput` fields from their runtime-only `TeamClosureAuthority`. An activation proof derives a current active participant attribution. Registered system sources resolve a closed `TeamSystemClosureScope`; the local `team-run` source may authorize only its exact default-topology completion, cancellation, or pre-publication creation failure. Providers re-resolve the proof while holding the relevant Team and channel serializers before replay, policy, or durable acceptance, and persist only the derived `TeamClosureActor`, never the proof or source scope.

`transitionTeamPhase()` likewise accepts JSON-only fields plus an opaque `TeamSystemPhaseProof`. Its closed system scopes authorize `team-run` to resume one stalled Team to `active`, to move one human-receipted default final from `active` to `quiescing` before local release, and `team-scheduler-dag` to move one active Team to `stalled` with its exact reason. The finalization scope binds the final channel, Envelope, human, coordinator, and Team cursor; the provider validates them with the final channel under its serializers before close policy or journal acceptance. No generic lifecycle actor or raw phase transition remains.

Terminal channel and Team-journal compaction also split JSON-only prefix fields from `TeamSystemMaintenanceProof`. The scheduler's only scopes bind the exact Team/channel, observed cursor, and `throughSequence`; providers resolve the proof again under their serializers before policy, audit repair, checkpoint writes, or irreversible source compaction. Historical `TeamClosureActor` values remain durable attribution only and never authorize maintenance ingress.

Soft interrupts split by owner as well. `team-run` may request only its current default human-to-coordinator interrupt through `TeamSystemInterruptProof`; its scope derives both participants and channel topology. Activation-bound Links list or acknowledge an interrupt only with their private `TeamActorProof`, from which the provider derives the exact target binding. No interrupt request, pending read, or acknowledgement accepts caller-selected participant, activation, Session, or provider fields.

`requestParticipantInterrupt()` resolves an active agent's idle or running binding, records its exact activation/Session/provider target, and runs `interrupt` policy. Only that target may list and idempotently acknowledge the request; it neither cancels a Team nor settles a turn. `upsertHumanAction()` and `resolveHumanAction()` accept only Team/cursor fields plus `TeamSystemHumanActionProof`. The Host API proxy retains an exact verified pending action or terminal resolution scope, and a provider re-resolves it under the Team serializer to derive the durable action, policy actor, and timestamp; a Host that no longer owns that entry fails closed. A settled action retains its request details and outcome for restart-safe Team reads. `recordUsage()` accepts a current activation proof and JSON-only provider/model facts; under the Team serializer, a provider revalidates the binding and derives Team, Participant, Session, and timestamp before parent-charge repair, replay, policy, or durable accounting. It is the provider seam for idempotent Session turn/step usage samples and a durable Team-subtree token/turn/cost aggregate. A child Team commits its local sample before propagating an idempotent parent charge; an unsettled charge blocks new child work and is repaired before later admission. A Hub may snapshot provider/model `usageRates` at Team creation to price samples that omit provider cost; an explicit sample cost always wins. `inspectQuiescence()` gives completion policies a detached list of active tasks, live activations, open channels, and pending human actions without mutating the Team. A typed cancellation request is durable before resource teardown; its `cancellation` projection distinguishes an admitted stop from terminal `closure`.

`TeamRootCreateInput` receives a required goal seed, typed Team resource budgets, and an optional immutable authority grant. Its runtime request requires `TeamSystemRootCreationProof`; the current `team-run` source binds the complete root payload before a Team identity exists, and the provider revalidates that proof after `register` policy and after opening the new stream before its first append. A proof-owned root retains its non-secret system `createdBy` provenance in the Team record, snapshot, and checkpoint. `TeamChildCreateInput` is likewise JSON-only, but its runtime request requires `TeamSystemChildCreationProof` with the complete child payload and one observed parent cursor. The only accepted source name is `team-child-delegation`, which shipped compositions intentionally do not mount until a parent-task delegation consumer owns it; raw child creation therefore fails closed. A provider resolves the proof before parent repair, under the parent lock, after register policy, and after opening the child stream. Neither hierarchy data nor a parent task reconstructs that proof, and the child journal retains no reusable credential. `TeamSnapshot` and `TeamStateSnapshot` expose the current `TeamGoalSnapshot`; it carries the owning Team id, a goal-local revision, objective, phase, optional blocker, and goal-specific budgets. Child Teams and Participants can only narrow their parent's operation, workspace, scope, and typed budget grant. `updateTeamGoal()` and `transitionTeamGoalPhase()` accept JSON-only goal fields plus an opaque `TeamActorProof`; the provider revalidates the current human or activation authority under the Team lock and derives the policy participant before commit. The update changes objective text and/or goal budgets without changing phase; the transition uses the same fence, and `blocked` requires a blocker while `active`, `paused`, and terminal `complete` omit one. Team failure and cancellation remain Team lifecycle facts.

`archiveTeam()` splits JSON-only `TeamArchiveInput` from a runtime-only system or authenticated-human proof. `team-run` may retain an in-memory terminal owner after settling its own Team; its exact system scope contains the Team and observed cursor. An authenticated human proof binds the same complete input to one active human Participant with `close` authority, so a detached or restarted terminal Team remains archivable without reconstructing a TeamRun owner. A provider resolves the proof before loading the Team, again under the Team lock (including an already-archived idempotent read), and once more after `close` policy before appending the unchanged `team/archived` record. No Team id, archived snapshot, roster data, or restart reconstructs either proof; proofs are never written to a journal, checkpoint, or wire request.

Participant invitations freeze a duplicate-free capability list for later scheduler eligibility. `ParticipantInviteInput` and `ParticipantPhaseTransitionInput` contain only JSON fields; trusted topology sources use `TeamSystemTopologyProof`, while authenticated product calls use `TeamHumanActorProof` for non-human participant invite and phase mutations. Human participant creation remains restricted to trusted topology/bootstrap sources, and the Host/SDK wire never supplies an owner. The `team-run` source may issue bootstrap invite/phase scopes before it publishes a Run, a declared worker's `provisioning`-to-`active` scope after publication, and reviewer invite/phase scopes for lazy provisioning. The same proof opens only the first direct-v3 human/coordinator channel. Generic non-workflow channel opens and ordinary closes require an exact `TeamSystemChannelLifecycleProof`; its runtime-only dispatch marker selects the generic route, while the registered source binds the complete JSON payload. Providers resolve topology or human scopes before participant policy and again under the Team serializer before append, so raw participant ingress fails closed. Task creation freezes ancestry, required capabilities, priority, filesystem scopes, workspace mode, budget, a closed review route (`none` or one participant), and `maxAttempts`. Every task creation carries a retry `createCommand` with an idempotency key and a runtime proof. A coordinator proof derives its activation creator; an authenticated-human proof binds the complete parsed input and derives a durable human creator containing only Team and Participant ids. The provider revalidates the proof before replay, policy, or append, and no wire input includes creator identity or a proof. Workflow-plan admission likewise uses a coordinator proof and derives its durable actor. A task may retain an advisory `proposedOwnerId`; it is a scheduler hint only and never grants authority. A task carries either no lease or one current lease for an `assigned` or `running` attempt. An assigned lease has no start time; a running lease has one. Its `attemptCount` equals the settled attempt history plus that lease, whose task-local ordinal and id are never reused. A lease retains its assignment revision and may retain an attached wake channel. Agent-owned leases retain an `ActivationId`; human and service leases omit it. Owner operations repeat that exact epoch, so a stale residency cannot renew or settle a newer lease.

`assignTask()` mints the lease and may retain an attached wake channel; `startTaskAttempt()` requires the exact revision, attempt id, Participant, and applicable activation. `heartbeatTaskAttempt()` and `settleTaskAttempt()` take an opaque `TeamActorProof` plus JSON-only task, attempt, and revision identities; settlement additionally accepts only `released`, `failed`, `completed`, or `cancelled`. Under the Team/task serializer, a provider resolves and revalidates that binding, then derives the Team, Participant, activation, and Session before renewing or settling the lease. `claimTaskAttemptStart()` takes an opaque `TeamActorProof` plus only JSON-only task, attempt, assignment-revision, wake-channel, and accepted task-Envelope identities. Under the Team/channel serializers, a provider resolves and revalidates that binding, derives the Team, Participant, activation, and Session, then binds the assignment delivery; repeating that exact current claim returns the running task without another journal record. `expireTaskAttempt()` requires the revision and attempt id after its deadline. A completed attempt retains a summary; a failed attempt retains a code and message; artifact references remain outside this definition. A `none` review route may complete an accepted attempt directly; a participant route records each reviewer decision against one completed attempt, including its nonempty reason and selected `completed` or `pending` phase. It retains exactly one unresolved completed attempt only while the task is in `review`. `resolveTaskReview()` requires the configured reviewing Participant and records that decision through `task-mutate` policy. `proposeTaskOwner()` changes only the advisory proposal on an unleased pending task, validates that a named Participant belongs to the Team, and lets the scheduler fall through when that Participant is not otherwise eligible. `deleteTask()` rejects a task awaiting review so an unresolved completed attempt cannot be discarded. `updateTaskDetails()` changes only instructions and dependencies after the provider verifies no current lease; it cannot rewrite task phase, scheduler facts, or attempt state.

An integration task adds an immutable source task/attempt, provider, target, expected target revision, and proposal or merge mode to that same task record. Its completed attempt must retain an integration result whose target fence matches the task; integrated results include the resulting target version, conflicts include paths, and the final verification and artifact manifest remain in the ordinary durable attempt result. The Hub validates the source attempt and runs `workspace-integrate` policy before admitting the task, then validates the result again after task policy and before the task CAS append. The workspace provider still owns bytes and Git operations; this Team record owns the integration task's authorization and outcome.

Direct attempt start now derives its Team, participant, and activation from `TeamActorProof`; task details edits and tombstones require a current coordinator proof. None of these requests accepts caller-selected owner, participant, or activation identity, and every path revalidates its proof after `task-mutate` policy before append.

`assignTask()` and `expireTaskAttempt()` accept JSON-only task/lease fields plus `TeamSystemTaskLeaseProof`. Only `team-scheduler-dag` may resolve an exact selected assignment or elapsed attempt; the provider re-resolves that scope before parent-charge repair and again under its Team and attached wake-channel serializers before policy or commit. A scheduler revokes the proof after the call and closes a just-opened wake channel when assignment did not commit.

Scheduler review, wake channel, and delivery-expiry lifecycle uses the separate `TeamSystemSchedulerChannelProof`. Its closed scopes open one participant-review consult channel for an exact completed attempt and idle reviewer binding, open one self-addressed task-assignment wake channel for an exact pending task and idle activation, close one unleased orphan wake channel with its fixed diagnostic, or expire a bounded due-delivery prefix for one exact Team/channel cursor and scheduler clock observation. A provider validates the source scope before repair and again under the Team/channel serializers before policy, channel creation, attachment, close, or expiry append; a wake channel referenced by any current task lease is never eligible for cleanup. These proofs do not assign a task or post an Envelope.

Workflow compiler mutations use `TeamSystemWorkflowProof`. A channel open that names `workflowPlanId` requires its compiling plan revision, current coordinator binding, and an exact TeamRun scope; plan channel/task bindings and ready or terminal phases require the corresponding proof as well. An attached workflow channel may be closed only through the separate orphan-cleanup command while its compiling plan has not bound it, so generic channel authority cannot retire the plan's bound channel.

Current-coordinator default-worker owner proposals and task cancellations use `TeamSystemTaskControlProof`. The source binds the exact coordinator, task revision, and proposal or cancellation payload; a provider re-resolves it under the Team lock and verifies the task's durable creator provenance before policy or append. Post-release cancellation cleanup uses a separate `TeamSystemCancellationCleanupProof` bound to one durable cancellation identity and one pending task or active channel. Completion cleanup uses `TeamSystemFinalizationCleanupProof` bound to a human-receipted final, the default human/coordinator topology, and one active channel. A provider revalidates either proof's exact cursor and durable facts before policy or durable append; neither proof authorizes generic task or channel mutation.

An activation-bound Link holds a `TeamActorProof` lease privately. Its receipt input contains only channel, Envelope, and observed-cursor fields; the provider revalidates the proof while holding the Team/channel serializers and derives the recipient before receipt policy or WAL admission. Heartbeat input contains only `taskId`, `attemptId`, and `expectedRevision`; settlement adds its typed outcome. A provider resolves the proof once to select its Team serializer and revalidates it while holding the Team lock before it derives the Team, Participant, activation, Session, and exact current lease owner. Ordinary Link `post()` and review requests retain their own typed contracts, and Team-closure authority is outside this receipt boundary.

Providers call `registerAdapter()` to make one synchronous, pure channel adapter available under an exact `(type, version)` identity. Registrations are effect-scoped and HMR-safe. A channel manifest freezes that identity and its participants, while the channel WAL stores its lifecycle edges separately.

Providers call `registerPolicy(hook, policy)` to compose governance around `register`, `invite`, `activate`, `channel-open`, `send`, human-action, usage, `dispatch`, goal mutation, task mutation/assignment, interruption, workspace allocation/integration, and close operations. A policy that permits an operation calls `next()`; a policy returns a structured denial without delegating. `authorize()` returns the composed decision. Providers emit `team/changed`, `goal/changed`, and identified `channel/changed` notifications only after their durable commit point; observer failure is contained and logged. `readAudit()` exposes a bounded source-cursor projection maintained by the provider for the Team journal or an attached channel WAL without making it authoritative. `compactChannel()` and `compactTeam()` are provider-owned maintenance commands whose implementations must preserve source cursors and verify terminal-channel or Team-journal watermarks before removing history. A compacted channel snapshot and audit page may disclose their first retained cursor so consumers can resume without guessing the retained boundary. `getMetrics()` includes compaction, checkpoint-failure, audit-projection repair, and audit-failure counters alongside the existing process-local counters.

`TeamTelemetryCoordinator` is the optional capture Consumer for those feeds. It emits detached Team-journal, channel-WAL, Session model/tool-span, and lifecycle records, copying the known Team, Participant, Activation, Channel, Envelope, Task, Attempt, Session, provider, model, trace, causation, and correlation identities into primitive attributes. A `team-telemetry/record` waterfall is the deployment redaction/enrichment point; sink batching, retry, loss, export, and alert thresholds remain provider-owned. The coordinator contains observer and sink failures so telemetry cannot interrupt an authoritative append or model loop, and forwards Session flush hints before backend shutdown.

The definition also owns the JSON-only `TeamWorkflowPlan` vocabulary. A provider can admit one complete plan, bind its task templates and workflow channel through compare-and-set revisions, and transition it from `compiling` to `ready` or a terminal projection. Plan-local task and channel identities are separate from Team task and channel ids; a consumer remains responsible for resolving participant roles and versioned graph extensions before admission.

Channel snapshots may expose `replayWatermark`, the highest source cursor before the earliest still-pending recipient Envelope. Link reconnects start after this durable bound; terminal-channel compaction must pass the same watermark and pending-delivery checks before removing source history.

The local Hub's metrics add pending-delivery depth, active activation/task counts, stalled-Team count, replay lag, latest task-attempt latency, latest receipt latency, workspace-conflict count, and cumulative task/receipt latency histograms to the existing counters. Histograms use the fixed Team protocol boundaries and cumulative positive-infinity bucket. These values are operational snapshots; they do not authorize or reject a business mutation.

`admitTeamFinalResult()` accepts an exact final Envelope, WAL sequence, content fingerprint, Team-scoped retry key, and `TeamSystemFinalReceiptProof`. The provider derives the human recipient and durable owner from the proof and Team membership. Its `TeamFinalAdmission` records independent acceptance by the closed `team-run-result` sink before a system final receipt; it grants no principal inbox, display, or general human mutation authority. Identical retries return the original admission; another key or changed selection is rejected. The admission and referenced WAL content remain retained for the Team lifetime.

`ActivationBindingSnapshot.fencedAt` records provider-confirmed termination while closure-owned allocations remain unsettled; it is immutable and does not imply full quiescence. `quiescedAt` still requires released allocations and settled task leases. `requireSystemClosureDriverProof()` resolves only a live runtime token; its consumers must also check the exact durable intent, Team cursor and resource epoch before acting. A controller closure-stall scope binds that intent identity and epoch without permitting resume, replacement, or a new closure.

`getTeamSelection()` is a separate read-only projection for initial selection: bounded display text, exact coordinator binding, lifecycle and collection counts, without history arrays. Host exposes `team.selection`; the TypeScript and Python SDKs expose `team/selection`. Full `getTeam()` remains explicit for consumers that need authoritative replay state. `includeMetadata: true` adds exact goal, budgets and usage only when the complete response fits the same byte allowance; an explicit unavailable result preserves the lightweight selection on overflow. Pending human-action counts and cancellation text remain bounded display data.

`getMemberSession()` resolves one exact member’s latest published Session binding, including offline history, without activation side effects. The response omits supervisor configuration and is bounded by the Hub’s `maxSelectionBytes`. Host exposes `team.member.session`; SDK clients use `team/member-session`.

`getHumanAction()` reads one current durable action by Team/action identity under `maxSelectionBytes`. Missing and oversized actions fail without a full-state fallback. Host `team.action.read` and SDK `team/action-read` preserve that selection; reading never admits an answer.

`browse()` returns typed task/member/workflow summaries under a complete-page byte limit, separate from full-record APIs. Display prefixes disclose truncation; ids and protocol roles remain exact. An oversized role rejects its row. The provider resolves omitted limits from its configuration. Host uses `team.browse`, and TS/Python SDKs use `team/browse`. Ordinal-prefix work is reported in `scanned`; cold hydration remains internal.

`inspectTask()` selects `record`, `attempts`, or `reviews`. `record` omits both history arrays and returns their counts; history pages use direct array cursors and an optional `expectedRevision` fence. The Hub applies `recoveryPageSize` and `maxSelectionBytes` to the complete result. Oversized individual records reject; history pages remain independently readable. Private result, child-result and integration artifact references are omitted. Host uses `team.task.inspect`; TS/Python SDKs use `team/task-inspect`.

`inspectWorkflowPlan()` returns current metadata and one revision-pinned task/dependency window. It omits instructions, protocol graphs and result bodies, caps the whole response with `maxSelectionBytes`, and reports template/binding lookup work in `scanned`. Host uses `team.workflow.plan.inspect`; TS/Python SDKs use `team/workflow-plan-inspect`. The complete internal `getWorkflowPlan()` API remains explicit.

## Model Experience

### Team definition

#### What the model sees

`ctx.teams` registers no tools, prompts, model inputs, or model outputs. A provider or consumer owns any model-visible Team projection.

#### Token effect

Zero.

#### KV Cache effect

This package does not affect cache reuse.

## Known Limitations and Deferred Work

- `clocky-team` is a Service Definition, not a provider; use `clocky-team-hub` for local durable Team journals, channel WALs, recovery, checkpoints, and creation-time limit enforcement.
- Scheduling, remote Links, remote reconnect transport, and product APIs remain outside this definition and the current local Hub. Providers may reject the optional durable interaction and usage methods when those capabilities are not composed.

### Single-task cancellation

`cancelTask()` retains a revision-fenced single-task intent; `TeamTaskSnapshot.cancellation` identifies its exact work. Live attempts remain non-terminal until owner acknowledgement or activation quiescence and allocation release. An elapsed lease deadline does not reopen a cancelled attempt. [Cancellation ownership](../../../.agents/notes/implemented/architecture/2026-09-06-exact-single-task-cancellation.md).
