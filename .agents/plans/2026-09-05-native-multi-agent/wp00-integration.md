# WP00：共同基线、接口登记与集成

主责：技术负责人。交付对象：全部程序员。优先级：开工前。依赖：无。必读[总计划](overview.md)、[接口约定](contracts.md)、[验收映射](acceptance-map.md)。

## 目标与范围

给全部开发者一个包含已审计实现的可复现提交，避免重复实现或从不完整工作区开工。负责共享接口与格式版本登记、热点文件集成顺序、P0 放行和最终候选提交；不替代功能包作者的实现和测试责任。

当前工作区包含大量与本计划无关或未经独立确认的修改。不要整树 add/commit，也不要丢弃别人的变更。先由每项修改的 owner 确认应进入共同基线的文件，再建立干净集成分支。

## 工作步骤

1. 记录 HEAD、staged/unstaged/untracked 清单；确认 Team、product-principal、closure-driver、channel-view、bundles 和 SDK 文件是否完整。用工作树 diff 和关键文件哈希描述实际基线，不以 HEAD 单独代表它。
2. 由相关 owner 确认准备提交的代码和文档；形成同一可复现提交。记录构建依赖与已知失败，不把历史局部测试复制成新提交的成功证据。
3. 为每包创建独立工作区和分支；采用仓库的 codex/ 前缀。所有工作区从具名共同提交或已确认的依赖 PR 开始，绝不共享一个可写 checkout 给多人。
4. 组织 C0–C7 接口登记。每个字段给出 owner、解析位置、authority、幂等范围、CAS、durable/wire 影响和失败场景。批准的是可运行增量的约定，不是预先合入全部未来接口。
5. 维护热点文件合并队列。功能作者保留对应函数/事件的逻辑所有权；集成人检查最新父提交后合并，重跑被父变更影响的场景。
6. 在 P0 当前提交上收齐 AUTH/LIFE/LEASE/VIEW/GATE。只要其中一项缺少证据，P1 的生产能力仍未获放行。
7. 把实际依赖映射到官方 PR stack。即使开发者使用多个并行分支，合入同一仓库的依赖链也不能以临时 retarget 操作绕过仓库 stack 规则。

## 接口与格式控制

每个合入切片登记 Team journal/checkpoint、channel WAL/checkpoint、Link、principal inbox、audit 和 SQLite schema 的实际版本。两个分支都修改同一格式时按最终合入顺序重新分配并重生成 fixture，不能保留两个意义不同的同版本解释器。

跨语言变更必须带 Host schemas、SDK protocol、TypeScript、Python 及调用方更新。消费者未就绪时切片保持未合入，或作为完整依赖 PR 一起集成；不能靠 unknown 字段、optional 全放开或兼容 fallback 保持假绿。

## 验证与产物

产物包括共同基线记录、C0–C7 登记结果、共享文件队列、已确认的 P0 放行记录和下游可 checkout 的提交。记录采用[交接模板](handoff-template.md)。

开工核验使用现有[聚焦检查工作流](../../skills/dsh-pre-push-checks/SKILL.md)。按真实 diff 选择命令；P0 放行所需整体验证由 WP01/WP13 执行并记录，集成人检查环境和提交是否一致。若父提交变化，明确哪些证据仍有效，哪些需要重跑。

## 验收

- 任一程序员仅 checkout 给定提交并按仓库命令安装，就能看到本计划列出的已实现基础；不会依赖另一个人的未跟踪目录。
- 每个 Gap 有一个主责，每个热点文件有集成次序，每个跨包字段有唯一语义 owner。
- P0 的未通过项可定位到失败测试或环境，不以“基础基本完成”代替放行。
- 每次合入后的格式、消费者与 fixture 一致，后续分支使用更新后的父提交。

## 建议提交拆分

第一项交付为基线和证据清单；第二项为接口登记与测试表达能力；之后按功能切片集成。不要单独提交没有生产消费者的空 Service、未使用 schema 或 disabled 新插件来宣称完成。
