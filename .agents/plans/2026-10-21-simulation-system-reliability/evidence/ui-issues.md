# Simulation 测试问题报告：UI 与信息展示

日期：2026-10-21。对象：Clocky WebUI 的 Simulation 案例入口、启动确认、运行概览、事项、历史、暂停和恢复流程。本文记录已观察的问题及改进建议，不表示这些建议已经实现。

配套文档：[系统与业务执行问题报告](system-business-issues.md)。停止边界、故障分类、预算计量和领域授权的系统约束由系统文档定义，本文只描述它们面向用户的交互与信息要求。

## 1. 审查范围与方法

本轮在既有登录会话中重新打开暂停运行，检查真实 DOM、导航、加载后的页面和弹窗，保存八个界面截图。没有启动推理、执行恢复、创建新运行或修改业务历史。审查结束时河港仍为第 12 天暂停，Native 修订 10241，模型用量结算记录 1,669 次。

运行中、错误及重连现象来自本次长测留存记录；本轮没有为重新演示故障而恢复运行。没有重新提交整个创建表单，也没有完成移动端、小窗口、读屏器、缩放和颜色对比度数值测试。相关条目会明确标为风险或待验证，不能当作已确认的无障碍违规。

参考原则：[状态反馈](../../.design-rules/references/hig/feedback.md)、[加载反馈](../../.design-rules/references/hig/loading.md)、[无障碍](../../.design-rules/references/hig/accessibility.md)。重点是让用户理解当前状态、操作结果和下一步，而非单纯更换视觉风格。

## 3. 详细问题与方案

### UI-01：列表陈旧状态与详情状态冲突

**状态：本轮复现，未修复，根因待定位。优先级：P0。**

**现象：** 同一河港运行在详情和 Native 中已是“第 12 天／已暂停”，返回列表却显示“第 11 天／已请求运行／仍有工作收尾”，上方另有“有更新·刷新核对”。一次刷新后的本轮观察仍显示旧值，不能因此直接认定刷新请求永久失败或指定某个缓存为根因。

**影响：** 用户可能误以为仍在消耗额度，重复暂停、重新打开甚至重启服务。轻量陈旧提示与醒目的运行状态相互冲突；“已请求运行”也容易被理解为实时执行状态。

**方案：** 列表与详情共享带修订号和观测时间的状态投影。暂停、恢复和检查点完成后，失效并重新读取对应列表项；陈旧数据保留时显著标为“上次观测：第 11 天，当前状态待刷新”，不能继续作为无保留的当前事实展示。刷新应有成功、失败、超时的明确结果，并保持原选择。

**验收：** 同一暂停回执之后，列表和详情最终显示同一已确认状态；网络断开或读取失败时显示“当前状态未知”，不假装仍在运行；跨标签页和重连可复现并验证；刷新不启动任何推理。

![运行列表中的陈旧状态](ui-audit/07-directory-stale.png)

### UI-02：缺少“运行至第 N 天”的明确控制

**状态：能力缺口，未实现。优先级：P0。系统依赖：SYS-10。**

**现象：** 开始/继续弹窗展示模型、每请求额度、区间额度、actor 上限等，却没有本次运行的终点或停止方式。本次第 12 天停止依赖向协调者输入要求以及人工监测，不是 UI 配置驱动的确定性保证。

**影响：** 用户无法直接设置可复现的实验边界，也难以预估何时可以离开页面。单独在 UI 放一个日期输入框而没有执行层约束，会产生虚假的控制感。

**方案：** 开始前提供“运行至模拟日/时间”“到达后暂停”“暂停后保存检查点”。若支持完成当日工作后再停，应明确区别于到达即停。运行头部持续显示目标与实际时间；修改目标必须显示对当前已受理工作的影响。

**验收：** 后端确认目标后 UI 才显示其生效；关闭浏览器不失去停止约束；恢复时保留原目标；超出目标的推进请求不能通过；保存失败仍显示已暂停，并可重试保存而不重启运行。

### UI-03：事项列表只有技术操作名，无法快速识别业务

**状态：本轮确认，未修复。优先级：P1。**

**现象：** 河港事项大多显示“未知领域：harbor”“execute”“v3”和截断哈希，申请者和目标是 `coop → harbor-environment` 等内部身份。可见行的“最近更新”为破折号。领域已经能够执行，因此“未知领域”不能等同于执行器不存在；它至少反映了展示层未形成可读映射。

**影响：** 多行看起来几乎相同，难以找出某天的报价、交付、取消订单或推进时间。排障依赖打开详情或到原始日志检索。

**方案：** 领域提供方注册经过权限检查的显示名称、动作摘要、主体名称、模拟日和业务结果。例如“供应商交付药品订单”或“协调者推进至第 12 天”，而不是统一 `execute`。未知扩展使用“自定义领域 harbor”这类准确兜底，不暗示运行失效。哈希保留为可复制的次级证据。

**验收：** 不打开详情即可区分报价、交付、消息和控制操作；日期来源明确，真实时间与模拟时间不混淆；无法展示摘要时解释原因；新领域无需修改主界面结构即可提供展示数据。

### UI-04：技术提交数被标成业务进度

**状态：本轮确认，未修复。优先级：P1。系统依赖：SYS-13。**

**现象：** 概览显示 79 个“业务已提交事项”。实际构成为 62 次 `act`、9 次 `advance`、6 次 `wake`、2 次案例 `checkpoint`。62 次 `act` 中又只有 45 次包含非 message 行动。一个 act 还可以包含多项动作，因此这些数字不能相互替代。

**影响：** 用户可能把 79 理解为成交或完成业务目标的数量。通用的 committed 状态也不必然证明某个案例裁判接受了业务，更不等于实现了参与者目标。

**方案：** 分开展示“技术请求”“业务决策”“含实质行动的决策”“控制操作”。对执行结果分别表达“请求已受理”“裁判接受/拒绝”“业务目标状态”。统计旁提供简短口径，进入详情后可追溯分子和来源。

**验收：** 本次数据能够准确解释 79、62、45 的关系；技术控制不增加业务成功计数；领域返回合法拒绝时不能只显示绿色成功；未知结果不计入已成功效果。

### UI-05：概览过多展示引擎指标，缺少领域业务摘要

**状态：本轮确认，未修复。优先级：P1。**

**现象：** 首屏大面积显示模拟时间和空日历，治理与外部世界卡片均为 0；人员卡片显示“在职 13”“非终止人物 14”和 writer、Participant、Activation。河港的技术席位不代表原始裁判中的真实雇佣；原始审计中的 18 笔未完成订单也没有在此获得对应的业务呈现。

**影响：** 用户可能误解技术绑定为真实社会状态；“当前没有需要你处理的事项”可能被读成没有业务责任；真正需要关注的库存、订单和逾期被隐藏在其他数据源。

**方案：** 概览分为运行摘要和领域业务摘要。运行摘要显示当前阶段、目标日期、最后进展、阻断原因和最近保存；河港业务摘要显示订单、交付、库存、现金、逾期和未决责任，严格遵守当前读取权限。技术席位、writer 和激活历史进入诊断区域。对不适用模块显示“不适用/尚未接入”，避免把零值与未映射混淆。

**验收：** 普通用户能解释当前发生了什么、是否需要干预；技术角色和业务角色明确区分；“需要处理”标为“需要人工干预的运行问题”，不替代业务责任清单。

![运行概览](ui-audit/01-overview.png)

### UI-06：长时间停在同一天时，缺少可解释的进展

**状态：运行中已观察，当前暂停页面未重新演示。优先级：P1。**

**现象：** 同一模拟日内可能有多个角色推理、裁决、结果收尾和压缩，页面主要显示“正在推进已受理工作”和不断增长的修订号。用户难以判断是正常长推理、模型纠错、队列等待还是卡死。

**影响：** 容易重复操作或误判运行异常；日志序号增长没有足够业务解释，也不能用它生成虚假的完成百分比。

**方案：** 增加只读执行活动条：角色、当前步骤、开始时间、最后有效进展、已用请求数、是否等待提供方。步骤应来自真实事件，例如“等待模型”“校验提交”“等待裁判”“处理结果”“保存检查点”。超过观察阈值时标记“较长等待”，不未经证据宣称失败。

**验收：** 对长响应、纠错、压缩、队列等待和进程失败分别有可核对的状态；断线时保留最后观测及时间，不继续动画暗示实时推进；活动条不得显示受保护的隐藏推理或其他角色私有内容。

### UI-07：权限提示正确，但用户缺少核验路径

**状态：本轮确认，未修复交互。优先级：P1。**

**现象：** 事项详情的正文显示“此内容需要单独的披露授权”；列表业务键及历史原文也受限。这是现有权限保护，不能简单判为读取 bug。但详情只剩技术状态、来源 ID，缺少说明当前用户到底可以核对哪些业务事实。

**方案：** 区分未授权、尚未生成、加载失败和不支持。展示已有授权覆盖的安全摘要，并说明受限内容类别和由谁配置权限；如存在授权工作流，提供其入口，没有则说明部署配置要求。不能为方便审查而默认开放所有角色私有视图或历史原文。

**验收：** 无权限时不泄露正文或可推断的私有摘要；有授权时可跳到具体业务证据；撤权后缓存不继续显示受限数据；用户无需猜测“无权”是否表示运行损坏。

![事项详情](ui-audit/03-detail.png)

### UI-08：持久历史默认偏向底层调试，定位业务事件困难

**状态：本轮确认，未修复。优先级：P1。**

**现象：** 当前运行有 10,242 条记录，默认从序号 0 显示创建、Team 预留及实体创建。主要筛选入口是技术记录类型；首屏不能直接回答“第 11 天谁交付了什么”。页面正确说明日志序号不是时间，但仍需要用户理解底层事件结构。

**方案：** 默认提供最近业务时间线，按模拟日、角色、动作、案件和异常筛选；将同一请求的多个技术事件折叠成一个业务过程。保留独立的原始日志视图、序号、源 ID 和导出，不删除审计证据。时间线的摘要必须由已记录结果构建，不能生成不存在的因果结论。

**验收：** 从一个订单或失败原因能够定位原请求、计划、裁判结果、通知和后续决策；能够直接跳到最近一次暂停与检查点；筛选与导出范围一致，权限受限有明确说明。

![持久记录](ui-audit/04-history.png)

### UI-09：故障原因和恢复操作缺少统一面向用户的表达

**状态：陈旧停止原因已修复，整体体验仍待完善。优先级：P1。系统依赖：SYS-11。**

**现象：** 余额不足发生时，曾显示“调度失败／已到本批工作上限”，实际原因需查 Session。部分旧运行当前只显示 `Simulation observation is unavailable`。虽然项目已修复前一批 stop 残留，但并未因此提供所有故障的安全分类和操作建议。

**方案：** 错误面板展示“哪个环节失败、当前是否还在执行、已完成结果是否保留、推荐下一步”。余额不足、限流、网络错误、schema 错误、历史不可读取等分开处理；不确定原因明确写未知。提供原请求查询和受控重试，避免用一个笼统“重试”按钮创建重复操作。

**验收：** 用户不读原始日志也能采取正确动作；原因不存在时不沿用旧错误；敏感诊断需要授权；恢复不会自动启动模型，继续调度仍是独立动作。

### UI-10：暂停、排空、保存与恢复的状态层次不够直观

**状态：行为已有保障，部分显示已修复，交互仍需改进。优先级：P1。**

**现象：** 需要理解 phase、driver、inFlight、writer 才能判断真正停止。已暂停时仍显示可用的“暂停调度”。保存或恢复期间可能同时存在本地旧回执与已完成的持久请求，要求用户理解“查询原结果”。

**方案：** 明确呈现“停止接收新工作 → 收尾已受理工作 → 保存中 → 已安全暂停”的过程；保留单独的仅暂停操作，并提供“暂停并保存”的常用入口。原 commandId 与回执机制保留在技术详情中，终态到达后主动对账更新主提示，不让用户猜测哪个结果更新。

**验收：** 重复点击不生成重复命令；断线后继续查询原请求；显示已保存时必须有持久完成证据；没有在途工作时明确显示已停止；恢复成功后仍暂停。仅查看弹窗不得产生推理。

### UI-11：恢复弹窗术语过多，默认信息顺序不符合用户任务

**状态：本轮确认，未简化。优先级：P2。**

**现象：** 恢复弹窗说明不回滚、不重放，属于应保留的优点；但“退休旧 writer”“返回暂停 owner”“保留后缀”和 Run/Team/Channel/Session 数量集中显示，用户需要了解内部架构才能理解。

**方案：** 首层说明“恢复第几天的运行、验证到哪个最新保存状态、恢复后是否暂停、会不会重复模型调用”；第二层提供覆盖范围与校验结果；第三层才展开源标识、序号和技术术语。不要为了文案简短而删除不回滚历史、不重放已完成调用的保证。

**验收：** 不懂内部组件的用户能准确说出恢复的效果；高级用户仍能复制全部证据 ID；过长运行名和不同语言下弹窗布局稳定，按钮含义不混淆。

![恢复确认](ui-audit/05-recovery.png)

### UI-12：额度与实际消耗缺少统一解释

**状态：额度展示可用，成本解释不足。优先级：P1。系统依赖：SYS-08/09。**

**现象：** 开始弹窗展示 262,144 单请求额度和每七 tick 1 亿区间额度。这是准入限制，不是即将支付的账单，也不是预计输出数量。运行期间的压缩、重试、缓存读取和未知用量又有不同口径。

**方案：** 将配置上限、已预留、已知用量、未知用量和可核实的费用分开展示；说明缓存读取口径。按业务、裁决、收尾、压缩分类，提供本次运行与主机共享池的边界。提供方不支持可靠费用查询时明确不可用，不按不完整 token 总量编造费用。

**验收：** 用户能解释预算占用为什么不等于已知消耗；主机并发与本运行预算不混淆；未知用量不按零计算；修改额度不能被误认为解除上游余额不足。

### UI-13：案例入口与部署适配关系不明确

**状态：本部署复查可见，产品发现能力待完善。优先级：P2。**

**现象：** 当前新建入口有模板、导入文件和空白定义，但只列出已安装的河港模板；仓库 test-cases 中的案例不会自然等同于可运行模板。读书节文件曾因 Git 忽略规则而在普通文件检索中漏掉，这也提示不能仅以一种文件列表判断案例是否存在。

**方案：** 提供经过授权的案例目录或明确的安装清单，展示来源、版本、适配状态、必需 provider、预期验收和模型建议；独立裁判案例应提示需要适配，不让用户尝试把任意文件当 World JSON 导入。不要自动扫描未经授权的任意文件目录。

**验收：** 已安装与仓库存在但不可导入的案例被清楚区分；用户知道下一步是导入、安装还是配置 provider；创建前能预检缺失依赖，且预检不触发真实推理。

### UI-14：视觉强调、术语与无障碍需要系统性整理

**状态：视觉风险已观察，量化合规待验证。优先级：P2。**

**现象：** 背景星点和纹理、较小的低强调文字、密集技术标识与中英文混用增加阅读负担。大面积空卡片吸引注意，关键状态反而较紧凑。已有明确键盘焦点边框和文字状态是应保留的优点。

**方案：** 降低背景装饰强度，把颜色优先用于状态和异常；统一中文显示名，例如“天”“当前运行实例”等，保留技术原名在详情中；建立正文、辅助信息、诊断字段的字号层级。小图标按钮补齐名称、目标尺寸和焦点反馈，动画尊重 reduced-motion。

**验收：** 用实际颜色测量对比度，不凭截图估算数值；验证键盘完整操作、焦点返回、读屏顺序、缩放和小窗口；状态不能只靠颜色；长文本、未知字段和加载切换不遮挡主要按钮。

## 4. 建议的信息架构

### 4.1 运行页首层

首层集中回答六个问题：当前处于什么执行状态；实际时间和停止目标是什么；谁在执行哪个步骤；最后一次有效进展是什么时候；有没有需要人工干预的运行故障；最后一个可恢复检查点在哪里。业务责任与人工运行干预分别呈现。

### 4.2 业务页与诊断页分层

业务页展示领域名称、可读动作、主体、模拟时间、业务结果、未解决责任及授权证据。诊断页展示 Native 修订、日志序号、writer、Participant、Activation、协议版本和原请求身份。两层共用权威数据，不维护相互矛盾的状态副本。

### 4.3 时间与结果口径

模拟时间、真实时间、最后观测时间分别标注。请求受理、技术提交、裁判接受、业务目标达成分别命名。陈旧、未知、无权限、不适用和数值为零必须区分，不能统一显示为 0 或破折号。
