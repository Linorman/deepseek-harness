01设计结论与本轮修正

推荐架构是“有边界的世界调控者 Agent + 确定性的世界执行内核 + 可插拔领域规则 + 持久化角色运行时”。 世界调控者不是一个只会转发消息的管理员，也不是可以随意改数据库的全能模型。它负责理解意图、提出世界变化、生成新角色、裁决未充分建模的情境，以及选择如何模拟外部世界；可信执行内核负责验证权力、维护因果与资源约束、实施变化并保存可恢复证据。

本轮相较上一版有四项重要修正。

第一，世界调控者成为明确的一等角色。 组织 driver 不再独自承担全部场景推进逻辑。每个运行可以有一个世界调控者，持有自己的 Participant、Session、决策与运行预算。它接收组织通过 Channel 提交的请求，并能够主动安排被场景授权的环境事件。

第二，“更新背景”成为版本化世界变更，不是改写全体 system prompt。 新制度、事实、角色、资源与外部事件都有身份、版本、生效时间、可见范围和来源。各角色看到的背景是这些记录的授权投影。

第三，自由裁决与硬规则共存。 模型可以决定一位虚构候选人的性格，或对没有专用模拟器的场景提出合理结果；不能因此伪造委员会批准、绕过资金守恒、修改已提交历史，或把模拟权限变成真实宿主权限。

第四，外部世界采用按需展开。 不要求预先创建世界上每个实体。世界调控者先复用已有外部身份，必要时调用规则模型、给出明确标注的环境裁决，或准备一个拥有独立记忆的外部角色 Agent。

系统中的每一个重要变化，都应能回答：谁请求、依据什么、谁裁决、何时生效、影响谁、哪些效果已发生，以及中断后从哪里继续。

目标与明确不做的事

目标是支持任意组织及其环境，而非只支持公司、CEO、HR。学校、医院、研究团队、城市社区、供应链与游戏组织都应能替换领域模块后复用同一运行骨架。灵活性来自可组合实体、关系、请求、规则、观察与效果，而不是从一个采购脚本扩展出越来越多分支。

第一版不追求分布式世界分片、不执行真实付款或任意外网动作、不让 Agent 动态安装宿主插件，也不承诺一份 seed 能使模型重新生成相同世界。先交付三个端到端能力：制度落地、动态人员变化、外部交互，并共同覆盖配置初始化、权限、日志和恢复。

03总体架构与责任分配

3.1 四个逻辑层，共用已有运行基础

层 主要所有者 负责 不负责
场景与用户控制 Scenario compiler、产品 administration、网页/CLI 定义初始世界、解析部署能力、确认启动与干预 从浏览器直接写 native 状态
认知与裁决 世界调控者、组织内角色、外部角色 理解、生成、交涉、提案、请求证据 直接赋予自己权限、提交未验证效果
世界运行与执行 World executor、领域规则、Native scheduler 验证、排队、提交世界变化、运行生命周期、对账 在 reducer 中请求模型或进行外部 IO
既有基础设施 Team、Channel、Session、Activation、Storage 身份、传输、日志、推理、启动/停止、物理存储 判断企业制度是否通过、招聘是否符合场景规则

实际因果链是：角色决策 → 原始世界请求 → Channel 通知与接收 → 世界调控者决策 → 已记录计划 → 权限/规则验证 → 世界效果 → 有界发布与角色后续观察。 普通沟通、既有合法资源转移和独立任务不必每次绕行调控者。它是需要生成或裁决的入口，不是每一次世界写入的人工串行瓶颈。

3.2 世界调控者的物理承载

MVP 采用一个 run、一个 canonical execution Team、一个调控者 Participant/Session。调控者对应保留命名空间下的认知 Entity，语义角色为 world-director，与公司内部职位无关。组织中的董事长不可以通过修改自己的 profile 获得这一角色。

可信 compiler 记录不可自选的 ExecutionRoleBinding，包含角色、允许的 operation families、版本与预算归属。普通场景数据可以选择“安装一个调控者配置”，但不能任意声明所有人物为系统调控者。Native admission 根据实际 entity、writer、decision 和持久化角色绑定验证权限。

这样的“控制角色”与“模拟角色”是逻辑隔离，不要求立刻拆成两个 Team。强行使用两个 Team 会引入当前 canonical binding 与跨 Team checkpoint/通信问题；暂时不值得。公司、部门、委员会属于世界实体，不自动对应嵌套 Team。未来独立子模拟可以引入 child Team，但需明确跨 run/Team 桥接与 checkpoint 支持，不能视为当前免费能力。S02S08S12S18

3.3 调控者的五项职责

受理与解释。 接收版本化请求，判断缺少哪些证据、需要哪个领域策略，必要时提出澄清而不是猜测批准已经发生。

生成与实例化计划。 将岗位需求、人物模板、世界约束与生成随机性转换为完整 Persona、外部实体定义或环境事件计划。

裁决。 对尚未由专用规则精确建模的情境，输出受约束、来源明确的世界结果；不能重写已知事实。

持续调控。 按授权场景日历提出市场、环境、人口或资源来源事件。主动干预必须有场景授权及独立预算，并留下触发依据，不能为了“让剧情顺利”无记录地干预。

解释。 输出可公开的裁决理由与依据引用，帮助用户定位阻塞、冲突和资源消耗。这里指结构化理由，不要求暴露模型内部推理过程。

3.4 为什么执行内核不能由调控者替代

模型输出不是执行凭证。它可能误读消息、重复生成、混淆历史版本，也可能遇到进程中断。执行内核必须核对固定 read-set、当前权限、实体/通道准备、额度、有效时间和已应用结果；然后把世界变化与结果一起持久化。

调控者可以选择“创建哪个候选人”，而执行器决定“这个候选人是否来自允许的模板、是否重复、何时具备行动资格、如何恢复”。这一分工不削弱调控者，而是使它能在长期模拟中承担可靠职责。

4.2 四种经常被混淆的“规则”

世界宪章限制整个模拟，例如不得逆改历史、真实工具禁用、资源来源模型和最大人口。只有真实用户授权的场景管理流程可以变更；普通公司委员会无法改它。

组织制度是世界中的事实，例如报销需要财务批准。它必须记录版本、适用组织、生效时间与制定证据。

可执行策略是已安装的可信规则实现，例如 approval.required/v1。制度可以引用它并配置参数，但不能把自然语言自动变为无限制可执行代码。

人物信念是某个角色相信的规则或信息，可能过时、错误或不完整。不能因为其进入背景就变成世界真相。

每个制度显示 enforcement: advisory | validated。advisory 通过授权上下文影响角色行为，也允许出现违规情节；validated 映射到具体操作准入检查。文本“禁止加班”若没有工时领域实现，只能作为可见规范，不能宣传成系统已验证所有加班行为。

4.3 事实、生效与可知时间

新事实至少保留 recordedAt（真实记录时间）、effectiveFrom/effectiveUntil（模拟有效区间）、visibility/availableAt（谁何时可知道）、revision 与 source。世界时间仍采用规范十进制字符串。

今天可以公告明天生效的制度：它今天已经可知，但明天才约束相关行为。相反，已经生效的私下董事会决定并不自动出现在所有员工的 Session。治理生效、通知发布、收件持久化和角色理解是不同事实。

“当前背景”是对这些事实的可重建视图。更新背景会追加新版本；旧 Decision 的输入和历史背景不能被替换成新版本。修正错误通过新更正事件或独立实验分支，不静默回填。

4.4 资源创建与调控

现有资源结算验证完整 read-set、同种类/单位、控制权与非负余额；初始账户创建是管理操作，不是模型 mint 工具。S03S19

保留这些约束。把“创建资源账户”“转移资源”“世界来源/消耗”“表现形式细化”拆开。调控者创建新人不能顺手给公司凭空增加资金；外部供应商从抽象实体细化成 Agent，也不能重复铸造库存。

世界层确实需要资源来源和消耗时，新增受策略限制的 resource/source、resource/sink 类效果：记录数量、单位、原因、来源模型/事件、额度和一次性授权。守恒关系改成明确的台账等式：期末总量 = 期初总量 + 已记录来源 − 已记录消耗，而不是授予无限 setBalance。

05场景协议与配置编译

5.1 一份定义，三种入口，两个不同用途

文件导入、网页表单、CLI/SDK 都操作同一种 ScenarioDefinition。第一版支持 JSON 与安全 YAML。编辑器可以在表单、组织表和代码视图之间切换，不能丢弃自己暂不认识的已安装领域字段；未知字段应明确拒绝或只读保留，不能静默删除。

场景定义用于创建新运行；当前运行由日志驱动。编辑模板不会复活已离职的人，也不会重置库存。对运行中世界的调整必须成为 WorldRequest 或经过认证的管理命令。

5.3 编译管线

parse → normalize → resolve references → validate semantics → resolve deployment → produce plan → confirm → persist → prepare。

5.4 输入与配置边界

客户端可以选择允许的模板和额度；服务端不能接受客户端声称的 capability、原生 proof、任意现存 Session ID。对运行配置进行变更需要新的版本化命令；历史重试使用原解析结果。

06请求协议：通过 Channel，但不把聊天当作授权

6.1 一个通用请求封装

建议模型侧新增逻辑 action world/request，不是一个新特权工具。其字段包括：领域/操作版本、目标对象、结构化意图、补充说明、依据引用、期望对象版本与希望的生效时间。请求者、run、decision、epoch、真实接收时间和原始 operation identity 由服务端派生。

典型领域请求是 governance.enact-norm、organization.hire、organization.end-employment、external.interact、environment.resolve-action。这五类不是全部支持范围；每一类走同一身份、证据、裁决和效果协议。

6.2 MVP 复用现有 direct-v4，而不是立即开发新 Channel adapter

为每个活跃认知角色准备一个与调控者的私有直接通道。不要把所有世界请求放入全员共享通道，否则招聘资料、财务请求和委员会机密会互相泄露。准备通道沿用现有 reservation/consent 流程；有历史请求的通道不复用为另一组成员。S06S07

提交 world/request 时，可信规范化步骤产生两个 native 操作：记录请求的本地效果，以及依赖该效果的标准 communication/post。请求 ID 在接受前由 run/decision/操作位置确定；通知文本包含严格编码的 requestId 与 payload fingerprint。这个文本只是索引，不是权限，也不是新的事实数据库。

两项意图和映射在同一次 Decision acceptance 中冻结。数量、消息和字节预算按展开后的操作计算。MVP 每个这类决策只允许一个逻辑 world request，避免复杂的用户操作索引重映射；后续支持一般批次时，必须保留逻辑到实际 operation index 的映射。

因此 transport.ts 仍然看到真正的 communication/post、固定发送者/接收者、固定正文、已应用依赖和精确 fingerprint，不需要放开任意 system post。新增请求记录的 schema/fold、规范化映射和 Session 工具结果需共同实现，不能只把一个 JSON 字符串扔进现有通道。S04S05

6.3 受理条件与后续通知

本地请求被记录后先处于“等待通知交付”，不是调控者已经处理。只有匹配的 Envelope/收件 Session 持久化事实就绪，才调度该请求的调控者决策。重复通知不会创建第二个 case；未知投递结果按现有 outbox 机制对账。

调控者从固定授权上下文获得真正的请求及证据，并可提出 request-more-evidence、reject 或 world/resolve。回复中必须区分“收到”“已批准”“已提交计划”“已生效”。

世界效果提交时原子记录一个结果唤醒。调控者在后续决策中读取真实结果，使用普通通信操作回复；固定格式的回执可由已注册确定性策略完成，不必再次调用模型。不能提前生成一封声称成功的通信，然后不论结果如何都发送。

6.4 两级幂等性

技术幂等性使用原始 request/operation/plan 身份及 payload hash：同身份同内容返回原事实，内容改变则拒绝。

业务幂等性防止模型用不同 decision ID 重复办理同一事项：同一岗位录用单的 hireIntentId、同一制度版本的 resolutionId、同一外部交互的 interactionId，各自有业务唯一约束。模型真的想再次招聘，需要新的招聘意图和重新校验岗位容量，不能靠改一个随机 ID 绕过。

真实用户管理命令可以走认证 RPC 直接进入同一请求/计划执行器，不必伪造一封来自 CEO 的 Team 消息。日志必须标记“用户干预”，并在需要时生成世界内通知。

07计划、裁决和原子提交

7.1 调控者输出的是世界计划，不是任意状态补丁

拟议的核心接口如下。它表达设计边界，不是当前可导入的 SDK 类型；生产实现还需要严格 parser、Branded ID、文档和错误联合类型。

interface WorldPlan {
  readonly requestId: WorldRequestId
  readonly baseRevision: number
  readonly readSet: readonly VersionedObjectRef[]
  readonly authorityBasis: readonly EvidenceRef[]
  readonly directorDecisionId: SimulationDecisionId
  readonly policyGeneration: PolicyGenerationRef
  readonly effectTime: SimTime
  readonly disposition: 'apply' | 'reject' | 'request-evidence'

  | { readonly kind: 'norm/enact'; readonly norm: NormVersion }
  | { readonly kind: 'entity/materialize'; readonly birth: BirthSpec }

  | { readonly kind: 'employment/end'; readonly request: EmploymentEndSpec }

7.2 对未充分建模世界的自由裁决

世界调控者可以在授权的 AdjudicationPolicy 下处理自由文本行动，例如“拜访一个尚未建模的行业协会”。策略为它指定可生成的结果类型、影响的对象范围、资源/时间上界、必需证据和可见性。

它可以选择一段合理的环境回应、一位接待人员的出生记录、一个延迟事件或一个明确的失败结果。输出写成 AdjudicatedOutcome，标记 scenario-generated，不能冒充真实外部观察或委员会记录。对硬不变量的检查仍由内核完成；对世界叙事合理性的裁决记录模型/策略版本和证据，允许真实用户审核。

已知事实优先于新生成内容。若供应商既有台账只剩 2 件库存，生成“现货 20 件”必须被拒绝或作为不可靠报价/信念记录，而不是覆盖库存。未知不代表零；未展开的信息保留 unknown，直到有合法生成/观察事件补全。

7.3 四种独立状态，避免一个万能 status

投影 示例状态 不应推导出的结论
请求处理 recorded / awaiting-evidence / planned / rejected planned 不表示实际已应用
授权与计划 unverified / approved / stale / superseded approved 不表示物理准备已完成
效果执行 pending / preparing / committed / blocked / outcome-unknown committed 不表示每个角色已经收到通知
通知与观察 pending / published / persisted / receipted receipted 不表示业务理解或接受

采用原始事实与当前投影，而不是把任意后来观察覆盖成“成功”。UI 将这些状态并列呈现。

7.4 本地变化与跨所有者步骤

纯本地计划在一个 Native append 中提交：世界事实/关系变更、计划执行结果、派生事件和审计引用同时成为事实。失败则保持先前状态。带 Team/Session/Channel IO 的计划采用持久化分步流程，详见人员生命周期。

模型规划发生在串行写队列之外；外部 IO 也不能占住 run 写队列。真正提交时在队列内重新核对 read-set、权限世代、审批、容量、有效时间、计划身份及旧结果。无关对象更新不必使整个计划失效；关键对象变化则记录 stale，产生显式新规划机会。

旧计划不能被无记录地“自动修正”。同一原始请求可以有后继 plan，但必须链接 supersedes 并保留旧方案，且该请求至多有一个成功的业务提交。规划重试数有上限。

submitted 的窗口提案还不是已接受计划。恢复时若旧 slot 被取消，不能把其中的计划直接执行；确需复用已记录的候选 Persona 或草案，由新决策引用并重新验证，保留新的接受身份，不伪造旧 slot 已完成。

08三个实例之一：CEO 与委员会颁布制度

8.1 把“委员会同意”变成可核验依据

MVP 增加最小治理协议：提案、投票、结案。提案固定正文内容哈希、制度修订号、委员会身份、投票策略版本、截止时间和 electorate。投票从真实绑定的角色决策派生投票人，不能由 CEO 提交一个声称“大家都同意”的字符串数组。

默认在提案创建时冻结有资格投票的人，支持一致通过与明确阈值。弃权、否决、重复投票和截止规则由策略定义。同一个人不能投两次；需要改票时以显式修订处理。投票结果绑定原正文 hash，CEO 修改条款必须重新审批。

GovernanceResolution 由确定性结案规则生成。它是业务证据，不是可以绕过当前服务权限的 runtime proof。世界调控者也不能生成假 resolution。

8.2 完整流程

步骤 行为 保留的证据
1 CEO 提出制度草案并通知委员会 proposalId、正文 hash、electorate、policy version
2 委员分别作出结构化投票 原 decision、投票人、choice、revision、时间
3 治理规则核验阈值并结案 resolutionId、票据引用、最终内容 hash
4 CEO 通过私有 world Channel 请求生效 WorldRequest 与确切 resolution 引用
5 调控者解释制度、确定可支持的执行映射 WorldPlan；advisory/validated 标识
6 内核复核授权与版本，在安全时点提交 NormVersion、有效区间、作用域、事件
7 向受影响角色公告 每个收件人的发送和接收事实
8 后续决策按有效时间和可见性取得制度 冻结的 context-view 与政策版本

MVP 可直接用通用治理领域记录，不强行把多成员投票塞进现有单 reviewer 的 Team task-review。Task 可以承载“讨论草案”的工作过程，但它不是投票真相；普通会议纪要也不是全票通过的证明。S12

8.3 生效与撤销边界

组织制度不能自动修改已有承诺的履行条件。默认只影响生效后的新准入；需要影响已有任务时，必须声明适用范围并生成明确的变更/补偿。撤销制度产生新版本和结束区间，不删除过去的执行证据。

委员会的人事变更发生在投票期间时，默认继续使用冻结 electorate；场景也可选择“成员变化使提案失效”，但必须在提案创建时确定，不能由调控者事后选择有利规则。

09三个实例之二：HR 招聘、角色生成与离职

9.1 招聘需求和候选人事实分开

HR 提交岗位、技能范围、薪酬/资源约束、已有候选人引用或“生成新人”的需求。权限来自当前任职与组织策略，不能来自 persona 中的“我是 HR”。调控者检查是录用已有候选人、从模板生成新人，还是先要求补齐 headcount/预算批准。

MVP 支持 hire-existing 与 generate-and-hire。后者允许在受控虚构世界中直接生成可入职人物；需要劳动力市场、候选人意愿、面试与 offer 接受的场景，后续使用同一请求协议扩展为独立生命周期，不默认“HR 一声令下就能强迫任何人入职”。

9.2 Persona 由调控者确定，但生成结果不能随重试改变

Persona 分三层：不可变出生事实（背景经历、初始技能和倾向）、可演化人物状态（关系、信念、技能变化）、当前职责与权限（来自任职和策略）。不要把职位写死成人格，更不要把业务职位当成 immutable Participant role 的可变值。

调控者提出完整 BirthSpec：来源模板/版本、生成输入引用、生成 decision、采样/随机记录、显式属性与文本、初始知识及 audiences、允许的执行 profile、业务归属。生成文本在被接纳为计划时持久化；之后才分配和启动运行身份。当前 model.ts 的 staged 列表只是局部暂存，因此这一步必须依靠 durable submission/acceptance，而不是以为 stage 已经足够。S04

同一请求在 plan 已保存后中断，重试直接使用已保存 Persona，不能再次生成另一位新人。只保留 seed 不够：同时保留实际输出、模型/提示配置版本和验证结果。模型生成的新属性不能包含 shell 权限、插件代码、任意模型 endpoint 或秘密引用。

MVP 可用有限字段和已安装 persona 模板生成；需要开放式、对低权限角色可见的长文本时，使用只接收准许输入的隔离生成上下文。调控者负责选择约束、委托生成、验证并确定最终人选，不要求所有生成都在其可能见过机密的单一历史上下文中完成。可复用同 Team 中有稳定 Session 的受限生成助手，而不是开放未计费的额外 LLM 旁路。

9.3 招聘执行的持久化步骤

阶段 具体工作 崩溃后如何继续
plan-retained 冻结 hireIntent、Persona、岗位与批准依据 查询原计划，不重新生成
reserved 预留岗位/所需资源额度及稳定 Entity 身份 同请求复用原 reservation；不得占第二个岗位
preparing 在维护边界准备 Entity、Participant/Session 和必要通道 使用现有 ensure/receipt 对账，不凭内存判断缺失

这里需要新增一个 native 级的 provisioning/ready 准入事实，与现有 Entity.phase 区分。原因是当前 preparation 要求 active cognition entity，而直接将半准备人物暴露给一般 scheduler 会产生竞争。准备中的 Entity 可以供受控 topology proof 使用，却不能开普通决策、成为合法新任务执行者或被 UI 标为已任职。这个 gate 必须进入 Native writer/decision admission，不能只加在网页上。S06S08

MVP 用短暂的全 run 维护暂停满足当前 paused provisioning 约束：调控者先提交计划并结束窗口，再由 owner 停止新准入、排空相关工作、prepare 并提交。不要简单去掉 paused 校验。后续的局部热变更仍需独立证明隔离、旧窗口和 controller 行为。

岗位/资源 reservation 也必须是可恢复事实，带上明确模拟到期事件或取消规则。执行失败不应永久占用岗位；释放是新的记录，已发生的 Team 历史和未知外部效果不能被当作未发生而擦除。

9.4 调岗、解雇和重新入职

调岗关闭旧 Assignment 区间并建立新区间，更新当前政策/上下文世代。Person、Participant、Session 通常不变。岗位空缺和新请求寻址从当前关系推导，不改写已接受任务的责任人。

离职先记录意图并阻止该任职继续取得新工作，再处理 open/submitted 决策、任务、承诺、待收消息和定时唤醒。需要停止认知时，先关闭新权限、撤销旧 writer，再等待 controller 确认 quiescence；只有确认后才能释放 resident slot。无法确认则保持明确恢复状态。

已接受的效果不能被取消操作悄悄删除。 当前结算会检查执行实体的 active 状态，发布也会检查收发实体。因此不能直接把人标 inactive 后假设所有旧效果仍会照常执行。MVP 默认在相关已接受效果得到明确结算/阻塞处置后才改变实体 phase；只结束任职时，可保留 active 身份用于独立的交接/个人活动，但撤销旧岗位权限。若要允许已 inactive 人物继续完成确切既有义务，需要额外的窄范围 reconciliation authority，不能顺便放宽全部操作。S05S19

已有 Team task 的执行者/已接受 commitment 的债务人不会因为“新主管上任”自动替换。MVP 支持等待完成或显式取消再建新任务；对不支持的义务转移返回 handoff-required。后续增加双方接受的责任转移协议，不伪造新执行者的既有证据。

重新入职创建新任职而保留人物记忆。terminated 用于真正不可逆的实体终止，不是普通离职。现有非终止人口上限和历史 Team participant 上限仍可能限制长期招聘；界面要把它们与在职 headcount 分开，不声称离职自动释放所有额度。S02S08S13

10三个实例之三：与未建模外部世界互动

10.1 分开“模拟外部”与“真实外部”

公司外部的供应商仍然可以处于同一个模拟 run。它不必是独立 Hub，更不意味着允许连接互联网。MVP 的全部外部交互明确为 simulated-only；真实网站、邮件、付款、现实招聘和其他现实副作用保持禁用。

未来真实连接器走独立 ExternalAdapter，要求宿主安装、资源/网络 allowlist、真实用户授权、幂等键和结果对账。调控者没有凭虚构世界中的批准获得真实凭证的权利。

10.2 按需选择表示方式

表示 适用情况 记忆与身份 对外来源标记
已安装规则/分布模型 快递时延、标准库存、简单天气/市场事件 稳定外部身份和已记录采样结果 simulated-rule
调控者环境裁决 一次性、无须独立人物视角的环境结果 case、结构化结果和 subjectRef director-mediated
独立外部角色 谈判、客户、监管人员、长期供应商代表 独立 Entity/Participant/Session simulated-actor
真实外部适配器 未来明确授权的现实交互 独立外部 operation 与真实 receipt real-adapter

“调控者自己模拟外部”可以表现为它直接裁决环境结果；涉及人物对话时，由它编排隔离的角色执行。不建议把调控者的全知 Session 换一段 system prompt，就当成供应商继续聊天。 那个模型可能已经看过买方内部底价，提示词不能使它从未看过这些信息。

环境裁决由调控者真实身份发布，附 subjectRef 和 director-mediated，不能伪造一个不存在的 Participant 发送者。独立外部 Agent 则使用其真实 canonical binding 和标准通道发言。当前 Team post 的发送身份从 proof 派生，不应为“代演”开放任意 sender 字段。S05S12

10.3 外部身份稳定，展开方式可变化

先按稳定业务 key、所属范围和请求相关键查询外部 registry。已有供应商就复用；不因每次新会话生成一家同名但库存和历史不同的公司。

一个非认知供应商组织可以先用规则响应，再增加一个认知代表，通过 represents 关系连接同一供应商。库存、合同和信用仍属于原供应商。这不是把现有 cognition:none Entity 原地改为 agent，因为当前 cognition 不可变。若某个外部人物将来明确需要认知，可一开始声明为 agent 并延迟 binding；否则增加明确的代表/认知代理身份，不改写其历史。S02

表示升级必须保留此前已经生成的事实、合同、报价及其可靠性级别；不得重复生成资产。降级则先停止 writer，再保留必要状态与记忆摘要，不删除记录。MVP 支持 latent/规则实体与按需新增代表；自动升降级和多表示切换留待后续。

10.4 一次外部交互的完整链

角色提出 external.interact → 请求固定在 native 并经 world Channel 交付 → 调控者选择已有/新外部身份与表示策略 → 生成并冻结外部计划 → 准备必要的代表与通道 → 在指定模拟时间引入回应/会面事件 → 角色取得授权观察 → 双方通过普通 interaction/task/resource 协议继续。

陌生外部实体可以不完整：未知库存保持 unknown，未知员工不必全部生成。以后新增细节受此前已知事实约束。实体、展开次数、生成调用、事件链长度和字节总量都有边界，避免一个请求递归创造无限世界。

11通用事件驱动与安全变更时点

11.1 Driver 不再写死业务剧情

通用 driver 只做：推进已接受效果、消费到期事件、收集 wake、选择候选者、保证驻留、冻结上下文、执行决策、按 slot 接受、返回明确停止原因。领域逻辑从制度、角色目标、世界请求与已安装策略进入，而不是在主循环中判断“下一步轮到买家”。

复用现有 collectDecisionWakes()、queueDecision()、reserveDecisionWindow()、openWindow()、ensureResident() 和 driveResident()。普通资源/任务效果继续使用既有执行器，调控者仅处理需要它负责的 case。S13S15

11.2 调控者不享有隐形的时间特权

一封发给调控者的消息必须等到配置的 deliverAt 且收件事实就绪。其决定成为后续调度 microstep 的效果，不能插入已经冻结的旧窗口。模型调用超时和运行监督仍使用真实时间；世界中的投票截止、入职时间和会面时间使用模拟时间。

MVP 只在没有开放 DecisionWindow 的安全边界提交结构/制度变更。角色运行期间可接收新请求，但这些输入只能进入后续固定视图。默认不 retroactively 修改已分配 slot 的背景或权限；强制撤权通过明确 fencing/cancellation 结束未接受决策。

计划请求的生效时间已经错过时，按场景预先选定策略返回 stale 或记录新的未来执行计划；不悄悄把过去时间重写成当前时间。

11.3 一个必须避免的死锁

错误链：调控者在打开的决策窗口中调用“创建新人”，等待新人激活；新人 provisioning 又等待 run 暂停与窗口关闭。

正确链：调控者只提交计划并结束自己的决策 → owner 关闭窗口 → executor 到维护边界执行 → 结果被记录并唤醒调控者/新人。任何工具调用不得在持有当前 window 时等待依赖该窗口关闭的 world mutation。

11.4 公平性、配额与驻留

调控者不必常驻。无待处理 case 时休眠；有请求、规划后续或系统事件时唤醒。管理模型调用计入同一个共享模型池和 native token 账，不存在免费的角色生成请求。

增加 per-run 的世界请求队列、每 case 决策上限、同一时间最大 world mutation 数、每周期实体出生与外部展开上限。可以给调控者设最小服务份额，但不能永久抢占普通角色；延续已有公平队列的等待龄规则。

MVP 的示例运行 profile 至少准备两个 resident 名额，且把调控者、生成助手和外部代表一起计数。进一步允许单 resident 时，需要证明收件、任务和调控者驱动在释放/恢复之间不会互相等待，不直接沿用纯采购场景的结论。被撤销但未确认停止的 writer 仍占容量。

不存在待处理世界事件时返回 idle/waiting-for-event，不是故障；预算、用户审批、未知外部结果和恢复分别有明确停止原因。run 在后台是否继续调度由已存在的产品 owner 持有，不能由 React 页面的挂载生命周期决定。S08S13S14

12信息边界、记忆与世界视图

12.1 三种观察者，不共享一份背景

普通角色视图包含身份、当前职责、合法行动、当前输入、相关目标/承诺、已知制度和自身授权知识。

调控者工作视图包含当前 case、结构化世界事实和足够的批准/资源依据。它不默认扫描所有人物完整聊天记录，也不把整张世界图塞进每次请求。

真实用户观察视图依认证策略决定是否可看全世界、私人角色记忆、调控者案件及源记录。运行所有者身份不能自动替代每一个内容权限；复用现有产品读取/失效模型。S10S11S14S16

12.2 每次模型输入都可从日志重建

沿用 simulation/context-view：固定 run/entity/decision/epoch、Persona/规则版本、选中的知识版本、Team Envelope 和 run event 引用、确切内容。模型 dispatch 前持久化并核对当前 writer。不要另用一个未记录的 director system-context 回调注入世界状态。

初始事实、制度、Persona 和自然语言报告需要明确来源。公司真实制度属于 world fact；“某员工听说制度已通过”可能只是 report 或 belief。世界调控者的总结也不是免责通道：摘要和推论必须保留授权来源，不能从隐藏输入推出可公开内容而不标明新的授权依据。

12.3 全知调控者的输出泄漏风险

字段过滤与提示词都不能证明模型没有把已见机密编码进自由文本。为此规定：调控者的广权限工作输出默认留在控制范围；向较低权限角色发布的结构化结果通过可信投影生成，只有明确获准的事实字段可降级公开。

开放式 Persona、外部角色对白或面向全员的自由文本生成，使用独立、输入受限的认知上下文；不能直接复用曾看过全体私密历史的调控者 Session。MVP 可以用已安装模板和受限字段避免复杂降级，或者配置同 Team 的隔离生成助手。后者计入所有资源额度，保持独立 Entity/Session 与最小能力。

公司与外部谈判者必须使用不同 Session。共用 canonical Team 不等于彼此可读取所有通道；角色只得到被选入其上下文的输入。浏览器的全知检查器也不能回流为角色模型的环境材料。

12.4 角色离职并不抹除记忆

默认人物保留已经知道的信息；离职撤销后续检索和岗位权力，不承诺忘掉旧 Session。需要真实信息隔离时，使用新的上下文隔离域和明确记忆转移协议，且处理派生摘要；这不是普通的 hibernate/resume。S18

只有当前小部分角色 resident 不代表历史自动可无限保留。知识检索、上下文、日志扫描、保留量和队列各有上限。必要时增加 checkpoint/index 与归档方案，保持可验证的引用，不静默删除仍被审批或效果使用的历史。

13原子性、崩溃恢复与可重复性

13.1 单一权威日志，多个物理所有者

新增 world request、治理、Persona 生成结果、计划、原子世界变化与执行进度写入 Native run journal 的版本化扩展。当前产品命令日志保留原始用户创建/管理请求及其结果引用；不能再建立一份能独立写入不同结果的 world 数据库。查询索引和 UI 汇总可以重建。

Team/Channel/Session 继续各自保存原始事实。相同 SQLite 后端不等于现有 API 提供跨日志事务；使用持久化意图、目标幂等键和回执进行对账。现有 checkpoint/restore 收集与验证跨所有者引用，恢复到可继续处理的暂停状态，不把世界回滚到旧 checkpoint。S12S14S15S18

13.3 重放、恢复与新实验不是一回事

记录重放只验证并折叠已记录事件，不调用 LLM、不访问真实外部系统、不重新抽样。恢复执行对未完成责任做受控对账，之后显式继续。新实验/分支使用新的 run namespace，可复用场景和已选择种子，但不保证模型输出相同。

模型输出被接受之后禁止为同一操作重新推理。未持久化的生成发生中断，重新尝试可能改变输出；这属于新的有记录尝试，不承诺 exactly-once inference。世界效果的防重来自身份、原子记录和目标去重，而不是网络 RPC 只调用了一次。

13.4 Checkpoint 必须扩展的内容

纳入 world plan/case/治理投票/Persona 版本、外部 registry、待提交 mutation/reservations、策略实现引用与 generation、调控者和生成助手/外部代表的 canonical Session、通道 generation 与结果通知责任。收集时先停止新准入、排空已接受 IO、确认 writer 状态，再确认跨所有者引用。

场景导出用于新运行；一致运行备份包含上述历史和所需跨所有者数据。MVP 可先支持同机已有存储上的 checkpoint 恢复，不把一份 YAML 或 native JSON 导出宣传成可移植完整备份。

14可扩展性：领域可插拔，不把一切变成任意 JSON

14.1 三个明确的扩展点

**领域定义（DomainDefinition）**声明请求、事件和效果 schema，纯验证/投影，以及已安装的确定性规则。组织、治理、外部世界是第一批实现；以后可以增加教育、临床流程的纯虚构运行场景、城市交通、制造等模块，而不修改调控者主循环。

**推理策略（Cognition/AdjudicationPolicy）**决定某类 case 由模型规划、确定性函数处理、等待人工，还是组合执行。世界调控者负责选择已授权策略，不能上传函数。

**效果适配器（EffectProvider）**负责跨所有者实际 IO、结果对账与关闭。它只能处理已接受、范围固定的意图；不能自造新的业务权限。

14.2 分阶段引入扩展能力

MVP 的外层 Native 操作明确增加 world/request、world/resolve 和必要治理操作；内层使用注册的 domain + version + operation 并严格验证 payload。最初只交付 organization/governance/external 三个内建领域，实现仍可在同一包中。

不要在第一版就建立任意跨实体查询语言、动态 reducer 编译器或通用插件 marketplace。先证明模块边界：新增一个“会议室预约”测试领域，只实现自己的 schema/校验/效果投影，即可经同一个请求和 Channel 流程工作，无需在主 driver 新增业务分支。

Native 的闭合核心不变量仍然保持闭合。当前 resource kind 等集合并非天然无限扩展；新增时间资源、空间或生产流时，需由所属资源所有者定义单位、合法变化与守恒规则，不能仅添加任意 kind 字符串就宣称完成。S03S19

14.3 生命周期与版本

按 Clocky 的 Cordis 模式注册，登记返回 disposer，贡献跟随 effect 生命周期；消费者依赖 Service Definition，不直接调用本地 provider 内部方法。采用明确的 resolve(request): Spec，把部署默认值解析在 owner 中。S01

已接受计划固定使用实现 generation。计划执行期间取得实现 lease；卸载关闭新准入并排空已接受工作。无法继续执行的版本显示 implementation-unavailable，不选择一个同名但语义已变的插件替代。

冷重放依赖对应事件 schema 和 reducer；缺失必需版本时禁止可写恢复。可额外提供明确标注不完整的只读原始记录检查，但不能把未知领域事件当成功忽略。跨包和 SDK 新增必需事件需要同步解析器、投影、replay 和快照。

14.4 后续多调控者如何扩展

先保持一个 run 一个最终提交顺序。以后可以把外部市场、人口、制度解释分配给多个领域调控者或生成助手：它们产生独立 plan，统一由 World executor 做冲突检查与提交。并行规划不等于多个无协调的世界写者。

只有当单机工作量、隔离需求和真实测试证明必要，才引入分区/多 run；必须定义跨区引用、因果时钟、幂等消息和 checkpoint，不能把增加几个 Team 当作完成分布式一致性。

实际命名可以随现有 API 风格统一；不能让客户端提交 Runtime proof、真实 sender、任意 native run spec。所有新 DTO 都提供浏览器安全类型与 parser。原命令请求应复用 Client runtime 的保留、查询与显式重试，而不是每张新表单各自实现一次超时重试。S14S16S17

15.2 创建工作区

入口是“模板 / 导入文件 / 空白场景”。编辑区包括世界背景、调控者、组织、人物、初始资源、行为与外部世界。先提供表格和结构化表单，辅以 YAML/JSON；图形画布是后续可替换的编辑视图，不拥有另一份业务真相。

预览清楚显示：将创建哪些实体、哪些 Agent、哪些系统角色；调控者的权限和预算；哪些制度只作为提示；外部世界是否真实联网；所有模型配置的实际解析结果。主按钮明确“创建暂停运行”。开始推理属于后续显式操作。

15.3 运行工作区

世界总览展示模拟时间、停止原因、待处理案件、人口与 resident/模型预算。组织展示岗位、任职和历史时间线；调岗拖拽只产生 preview。制度与背景展示版本、生效区间、审批来源和执行级别。世界调控者展示案件、请求证据、计划、生成角色和效果，不把一段长聊天当作全部运行状态。外部世界展示身份和表示方式。历史与恢复沿用操作、checkpoint、原请求与记录检查器。

优先呈现需要人处理的原因：缺少表决、预算不足、等待交接、Persona 不合规、外部结果不确定、writer 未确认停止。用户应能沿单一 case 跳转到具体 Decision、Operation、Envelope、Entity 和 checkpoint。

组织图不能仅用已加载的一页 Entity 假装完整世界。服务端提供有界查询并返回覆盖范围；大图逐步展开，历史时点固定 revision。当前视觉组件只读已加载窗口这一原则应保持。S16

15.4 运行修改、导出与撤权

修改模板副本用于新实验；修改当前运行提交正式命令。界面不能导出当前组织图后覆盖整个世界文件来“保存”。确认离职前显示未完成责任、资源控制权、消息与下属关系。

导出场景与导出运行备份是两个独立动作。默认场景导出不包含凭证、私有日志或调控者隐藏案件；完整导出必须使用明确权限。授权撤销时清除已显示的敏感文本和异步结果，普通断网则保留标记过时的数据与原命令，不自行提交第二次操作。S14S16

17MVP：必须真实完成的范围

17.1 一次可验收的 MVP，不是只有配置编辑器

MVP 包含 一个真实世界调控者 Agent、三个内建领域、一个事件驱动 owner、两种场景输入、同机持久化恢复。使用现有本地运行 provider 和 JSON/SQLite 后端，保持一个 canonical Team。没有真实外部副作用。

世界调控者 通过私有 Channel 收请求，真实模型决策，结构化 plan，后续结果回执 多调控者分布式写入
制度 固定成员提案/投票/结案、一致或阈值通过、制度版本与作用域 通用宪政系统、任意自然语言可执行化

调岗/离职 时态任职、未完成工作检查、正式退休/保留历史 无协议的责任自动继承
外部交互 确定性环境结果、调控者明确来源裁决、按需独立外部代表 现实联网/付款、自动复杂升降级

观察 请求、计划、制度、人物及外部实体的来源与状态 全量无界世界图和所有私密记忆默认公开

MVP 可以使用模板限制自由文本与效果类型，但不是固定买家/卖家流程。至少增加一个非公司配置样例，例如“研究实验室的项目组与外部评审”，只改配置与已有领域术语，主 driver 不新增业务分支。

17.2 首个端到端验收剧本

创建一家包含 CEO、HR、财务和委员会的公司；角色初始背景与私有信念不同。CEO 起草招聘制度，委员以独立决策投票；制度经 world Channel 提交给调控者并生效。HR 请求一位工程师，调控者确定 Persona，executor 准备其认知身份并安排入职。工程师向未展开供应商询问服务，调控者准备供应商代表，由独立 Session 回应。随后调岗并结束一段任职。

分别在 Channel 发布、Persona 固化、Participant 建立、业务提交、writer 退休位置杀进程；恢复后不重复投票、不重复招聘、不换 Persona、不重复资源变化、不把供应商变成全知角色。恢复保持暂停，显式继续后工作可完成。

这个剧本使用脚本化模型做确定性端到端验收，并增加一次显式、受预算限制的真实模型试验。真实模型试验只用于评估请求理解、Persona 合理性和裁决质量，不能替代故障注入及权限测试。

17.3 MVP 完成定义

所有新 public/persisted/tool 输入有严格 parser；所有世界变化有原始身份和来源；关键本地事实与派生责任原子提交；跨所有者执行有持久进度与精确重试；旧 writer 不与新 writer 共存写入；模型请求计费且输入可重建；错误明确区分拒绝、阻塞和未知；网页不确定结果不会生成第二次业务命令。

完成 MVP 不意味着证明任意规模吞吐、长周期无限存储、复杂制度语义或强隐私自由文本自动发布。界面和文档必须保留这些边界。

18.3 建议第一份 PR 的实际边界

第一份 PR 只做 M0 + 场景协议骨架：固定本轮 ADR、受控 operation/schema、版本/能力模型及最小请求 Channel 探针，不先大改 UI。第二份再做通用创建，将采购 foundation 从通用类型中分离。不要一次提交一个同时改 loop、全部页面、全部领域和持久格式的大型 PR。

M0 需要特别证明四个假设：控制角色的操作权限能在 Native 重验；展开的通信仍满足现有 post proof；半准备 Entity 不能通过 direct controller 绕过；调控者提交后不持有阻止 mutation 的窗口。任何探针失败都回到对应所有者修改契约，不用临时 bypass 掩盖。

19.2 最有价值的故障注入方式

在每个外部 await 前后和 native append 前后设置测试屏障，分别模拟错误、超时、响应丢失、owner 撤销和真正进程退出。断言具体身份、原始输出、资源余额、关系区间、receipt 和 writer 状态，不只断言某个函数返回 success。

记录运行中的模型请求数和完整 accepted 记录；冷重放路径断言模型计数不增加。Persona 未接受前的失败与已接受后的失败应有不同预期。故障测试不能依赖实时 provider；真实模型只用于另外的质量评估。

20风险、取舍与明确的默认决定

风险/取舍 本设计默认决定 后续改进触发条件
调控者过于全能 Agent 提案与可信 executor 分离，硬规则不可越过 新领域定义新的允许裁决范围，而非开放任意写入
自由裁决不够灵活 支持受限 AdjudicatedOutcome，缺专用模型时仍能产生环境事件 常见情境积累后以专用模拟器替代反复推理
调控者成瓶颈 普通动作直走 Native；模板/确定性规则可跳过模型；公平配额 观测到规划拥塞后增加领域助手
共享调控者历史泄漏 不默认读取所有私聊；低权限文本生成隔离；结构化结果可信投影 强隐私场景强制多个 scope 的认知执行
半准备实体可行动 Native readiness gate，不只 product flag 直接 controller 和恢复测试证明覆盖全部路径
全 run 维护暂停影响体验 MVP 接受明确的短维护边界，禁止无证热改 P2 通过并发/fault 证据后开放局部变更

外部代理不真实 把裁决、规则、独立演员和真实来源明确标注 质量评估决定更多情境需要独立演员
插件热替换改变历史 固定实现 generation、关闭准入、必要时拒绝恢复 支持显式、审计过的迁移，不静默升级

21最终架构决定与交付检查表

21.1 建议固定的 ADR

决定 结论
ADR-W01 · 调控者的权力 有认知与世界规划权，没有绕过规则的数据库写权
ADR-W02 · 世界真相 版本化事实/制度/关系是权威；背景与图形是投影
ADR-W03 · 通信与请求 Channel 保存可靠交付；Native 保存业务请求，两者精确关联
ADR-W04 · 生成与重试 保存实际 Persona/plan 后才进行运行时 IO
ADR-W05 · 组织与执行 组织关系不是 Team/subagent 父子树；MVP 复用 canonical Team
ADR-W06 · 外部模拟 按需展开、身份稳定；独立角色有独立 Session，不借用全知历史
ADR-W07 · 持久化 同 run 业务事实共享 native 原子提交；跨所有者用意图与回执
ADR-W08 · 运行期变化 MVP 安全维护边界；热变更须新增并发/恢复证据
ADR-W09 · 可扩展性 注册版本化领域和适配器，不向模型开放任意代码/JSON patch
ADR-W10 · 产品语义 计划、授权、应用、通知分别呈现；读取不等于运行

21.2 交付顺序的核心判断

最优先的工作不是继续增加几个模板，也不是先画一个完整组织编辑器，而是打通 “请求经 Channel 到达调控者 → 调控者真实决策 → 可验证计划 → 有记录的世界变化 → 冷恢复” 的纵向链。

这条链可靠之后，公司的规章、HR 的招聘和外部代表的创建都只是不同领域策略；新增学校、研究团队或社区，不必再改一套执行机制。

最终产品应让用户感觉自己定义并观察了一个会持续演化的世界，而不是在启动一个预先写好的对话脚本。 这种体验的基础是稳定身份、明确知识边界、真实的决策自主性，以及每一项已经发生的效果都不会因重启而失踪或重来。
